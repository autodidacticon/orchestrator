## Context

The daemon is started detached by `startDaemon` in `src/runs/lifecycle.ts` (from the `start` tool or `orchestrator-ctl start`), records `daemon.json` and `daemon.pid` in `~/.orchestrator/runs/<id>/`, and runs `Orchestrator.loop()` until `stop()` is called through the `shutdown` route or a signal (`src/main.ts`). It has no notion of activity: `verifierBusy()`, `pendingCascade()`, the store's launch and job tables, and the `events` long-poll in `src/operator/routes.ts` hold everything needed to decide whether anything is happening, but nothing reads them for that purpose. `daemonCommand()` resolves the daemon entry relative to the module that runs the MCP server, so the daemon always runs from the same installed tree as the server; `shimCommand()` in `src/runner/claude-code.ts` does the same for the per-agent façade. The plugin at `hosts/claude-code/` declares the server as the bare command `orchestrator-mcp`.

Pull mode already exists end to end: `claim` and `release` in `src/loop/orchestrator.ts`, the claimable launch state, the worker tools of the MCP server, the `work` skill, and `workflows/work.js`, which fans out worker subagents through the Workflow tool. Worker identity is an opaque `workerId`; the daemon does not know which session a worker belongs to, so a worker that dies with its session holds its launch until the lease expires (default ten minutes) and then spends a failed attempt. `release()` returns an untouched launch at no cost and fails the attempt after progress, removing the worktree in both cases; the branch is never deleted. Relaunch briefs already carry structured context (`AttemptContext` in `src/state/status.ts`: `priorFailure`, `conflict` with `previousBranch`, `revision` with `priorBranch`), rendered by `src/brief/compose.ts`.

Constraints: the daemon stays the sole writer of task state; every external effect sits between two durable records; the crash suite must keep passing unchanged; the sibling change `add-toolchain-discovery` owns check-command, integration-branch, and allowed-tools detection for spawned agents and is not designed here. Prerequisite: `replace-sqlite-driver` (planned separately, agreed with the owner on 2026-10-13) replaces `better-sqlite3` with Node's built-in `node:sqlite`, so the production dependency tree contains no native module; this change is applied after it, and its plugin-local packaging path assumes it. Until then the launcher's checkout and `npx` paths work as before.

## Goals / Non-Goals

**Goals:**
- A daemon lives only while a session is attached or work is live, plus a bounded window, and comes back transparently when a session needs it.
- Every daemon is visible: at session start, in `runs`, and in `status`.
- The plugin works from a checkout and from a marketplace install with nothing on PATH, and the daemon runs from the same tree as the server in both cases.
- The default experience from the plugin is visible session subagents; headless agents remain an explicit choice.
- A session ending mid-task costs no attempt and loses no work.

**Non-Goals:**
- Moving the loop into the MCP server process.
- Toolchain detection and the allowed-tools list for spawned agents (`add-toolchain-discovery`).
- Remote workers (`access: remote` stays reserved).
- Replacing `better-sqlite3`; that is `replace-sqlite-driver`, the prerequisite, and is not designed here.
- The reconcile defect that reaps an agent as soon as its report clears the lease, losing the final usage JSON and the log tail.

## Decisions

**The daemon stays a separate process.** Runs must survive crashes and session ends, which `crash-recovery` specifies and the crash suite tests: detached agents are adopted on restart, a verifier job in `publishing` is resolved by inspecting the integration branch, and a claimed launch survives a restart with its lease. Rejected: running the loop inside the MCP server process, so that it dies with the session. There must be exactly one writer per repository, and a second session on the same repository (two terminals, or pull-mode workers from several sessions, which `pull-runner` allows) would mean two loops over one store; verification must continue while no session is attached (a `claude -p` session ends the moment its prompt is answered, often before the verifier has published); and the MCP server is restarted by `/reload-plugins` and torn down with the session, which would kill mid-publish work that today converges after a crash. The daemon is kept and given a bounded life instead.

**Pull is the plugin's default, applied by the `start` tool at spawn, not a core default.** The core default `runner.mode` stays `spawn` and `orchestrator-ctl start` passes nothing, because a terminal start has no session to work in. The `start` tool, when it spawns the daemon without an explicit `mode`, passes `--default-mode pull`; `main.ts` turns that into the run's durable override only when the store has none and the repository's `orchestrator.yaml` does not set `runner.mode`, so an explicit choice in config or an earlier `orchestrator-ctl mode spawn` is never overturned by a revival, while a plugin-started run keeps `pull` across restarts whoever restarts it. `start` on a daemon already running with no `mode` leaves the mode alone, as today. The `run` skill then runs `workflows/work.js` itself when the mode in force is `pull` or `mixed`, with a worker count no larger than `capacity`, and monitors with `wait` as it does now; `work` stays as the explicit way to add workers from another session or to switch modes. Rejected: changing the core default to `pull`, which would park every launch of a terminal or CI run forever. Rejected: keeping `work` as a separate skill the user must invoke, which is the current state and the complaint. Rejected: passing `--mode pull` on every spawn, which would silently flip a run that an operator set to `spawn` when the daemon is revived.

**Session subagents need no allow-list; spawned agents do.** Workers run inside the session with its permissions and login, so the allowed-tools problem for headless `claude -p` agents belongs to `spawn` and `mixed` only. `add-toolchain-discovery` detects the check command, the integration branch, and the spawned agents' allowed tools and records their provenance in the run directory; this change references it and designs none of it. The two changes meet at `runnerCommand`: it is used only when a launch is spawned.

**Idle exit is a predicate over durable state plus request accounting, evaluated after every tick.** With `now` the orchestrator clock and `cfg = config.daemon`:

```
quiescent(now)   := no launch with status in {preparing, launching, live}
                    and no claimable launch whose claim window is finite and has not elapsed
                        (window 0 in spawn, runner.claimWindowMs in mixed, unbounded in pull;
                         a launch that a tick will spawn counts until it is spawned)
                    and no verifier job with status in {queued, checking, verified, publishing}
                    and no job in a terminal status with applied = false
                    and no pending cascade
attached(now)    := some registered attachment that is not ended and whose pid is alive
busy(now)        := inFlightRequests > 0
lastActivityAt   := max(startedAt,
                        end of the last request that is not a probe,
                        last tick end at which quiescent was false,
                        last tick end at which attached was true and cfg.exitWhileAttached was false)
idleMs(now)      := quiescent(now) and not busy(now) and (not attached(now) or cfg.exitWhileAttached)
                    ? now - lastActivityAt : 0
idleExitDue(now) := cfg.idleExitMs > 0 and idleMs(now) >= cfg.idleExitMs
```

A request is any call the loopback server dispatches, agent or operator, counted from arrival to response, so an open `events` long-poll is `busy` for its whole wait; the `wait` tool polls in twenty-second slices and keeps the daemon alive for as long as a session loops on it. A probe is `GET /v1/status` with `probe=1`, which `health()` in `src/runs/lifecycle.ts`, `runs`, and the session start hook send; probes exist so that listing runs never keeps a finished run alive. The check runs at the end of each loop iteration, after the tick, because the tick is the only writer and a ready task with free capacity has a launch by then; when due, the daemon appends `daemon.idleExit { idleMs }` and calls `requestShutdown` with reason `idle`, which is the graceful stop (`reap` false). There are no agent processes to adopt when idle by definition. Rejected: counting parked launches as live work, as the brief sketched. With `pull` as the plugin default a run whose session ended with launches parked would never exit; a parked launch is durable (`crash-recovery` keeps it claimable and re-prepares a missing worktree) and the next claim revives the daemon. Parked launches in `mixed` and `spawn` still count until spawned because a tick will act on them without any input. Rejected: a sleep-until-woken daemon without a window, because a terminal user who runs `start` and then writes the graph by hand needs time; ten minutes is that time, and `0` disables the exit for foreground use.

**Attachments count as activity by default.** The MCP server is a per-session process; it registers `{ id, pids }`, its own pid followed by its ancestor chain, with the daemon on first contact (and again after a daemon restart, since `pid` in `daemon.json` changes) and ends the attachment when its stdio transport closes. The daemon checks the first pid each tick, so a killed session is noticed within one tick. While an attachment is alive the daemon stays, like the MCP server beside it, and `daemon.exitWhileAttached: true` restores the request-only rule for people who prefer the daemon to come and go during a session. Rejected: the request-only rule as the only rule (the brief's "an open long-poll counts as an attached session"). It is kept as the fallback, but a session idle at its prompt for twelve minutes with a milestone under review would see the daemon exit and come back on `accept`, which is harmless but noisy in the daemon log and in `runs`; and with attachments registered for the session-end release anyway, the information is free. Rejected: a per-session `attach`/`detach` count without pid checks, because a crashed session never detaches.

**Exit records and revival on demand.** Every graceful exit writes `exit: { at, reason, reap, digest }` into `daemon.json` after `orch.stop()` and before the process ends, with `reason` `idle`, `stop` (the shutdown route), or `signal`, and `digest` from `digestOf`. A dead pid with no record is a crash; a daemon that starts overwrites `daemon.json` without `exit`. `reviveDaemon()` in `src/runs/lifecycle.ts` starts the daemon when the run directory holds `store.sqlite`, no healthy daemon answers, and the last exit was `idle` or a crash; `OperatorClient.url()` and the CLI's `resolveUrl` call it before every operation, so a session coming back after an idle exit, or after a crash with agents still running, sees the run as if nothing had happened; the first call pays the boot (recovery plus listen, about a second). After `stop` or a signal they refuse with the existing error naming the stop time and `start`, because an explicit stop is the operator's intent. A fresh repository with no run directory still needs `start`, which creates it. Rejected: always refusing, which turns every idle exit into a "call start" interruption of the run skill between `review` and `accept`. Rejected: reviving after an explicit stop, which would make `stop` meaningless for a session that keeps calling `status`. Rejected: a digest file rewritten every tick for the hook to read; the exit record carries the last digest, and an alive daemon answers a probe.

**A worker that dies with its session is released with `keep`; a worker that gives up is not.** `release` gains `keep`. With `keep` and observed progress, the daemon commits any uncommitted changes on the launch branch as a work-in-progress commit (`workspace.preserve`), ends the launch with reason `released`, removes the worktree, keeps the branch, and returns the task to `unstarted` with `attempts` unchanged and `carry.interrupted = { priorLaunchId, priorBranch, headSha, wipCommit?, reason }`; the next brief says the previous launch was interrupted, names the branch and head, and tells the agent to merge or cherry-pick it onto the new base or inspect it and start over. Without progress the existing rule applies (`unstarted`, no cost, worktree removed). While `waiting` the task becomes `blocked` with its question, as today, and the same context is recorded so that the relaunch after `answer` continues from the branch. This mirrors the conflict carry (`previousBranch`, "rebase that branch or start over") and the revision context (`priorBranch`), both of which already keep the branch and brief the relaunch. Because a kept release costs no attempt, a client that keeps dying mid-task would otherwise relaunch forever at no cost: the overlay entry counts `interruptions`, increased on every kept release and reset to zero when the task submits, carried in the `interrupted` context and reported with each live launch in `status`; `daemon.maxKeptReleases` (default 3, 0 unlimited) bounds it, and a kept release for a task already at the bound behaves as a release without `keep`, a failed attempt as today. Rejected: the existing release semantics for session end, under which the second attempt is spent by something the task did not do; with `maxAttempts` at 2 a session closed twice would block the task. Rejected: reusing the old worktree for the next launch, which breaks "fresh process per launch", the branch and worktree naming by `launches`, and the sweep rule that removes worktrees of ended launches. Rejected: keeping the worktree without committing, because the sweep would remove it and uncommitted work would be lost. The voluntary release keeps today's semantics because a worker that gives up after progress is reporting a failure with a reason, and its brief already carries `priorFailure`; a worker that must stop for an external reason passes `keep`.

**Three detach signals, in order of trust, then the lease.** An attachment ends when (1) the MCP server says so on transport close, which covers a normal exit, `/exit`, SIGTERM, and a killed terminal, because a dead parent closes the pipes; (2) the daemon finds the first pid of its chain dead at reconcile, which covers a killed MCP server; (3) the plugin's `SessionEnd` hook posts the ending session's process ancestry to every alive daemon under `ORCH_HOME`, and the daemon ends every attachment whose chain contains any pid in that list, which covers `/clear` and an interactive `/resume` switch, where the session process survives, the Workflow and its subagents do not, and the MCP server may or may not be restarted. The chain matters because of the packaging: under the launcher the server's parent is `node orchestrator.mjs`, and under `npx` there is one more layer, so the session process is two or three levels above the server and never its `ppid`; the server therefore registers `pids: [pid, ppid, ...]`, walked with `ps -o ppid=` up to six levels within 300 ms (`src/runs/ancestry.ts`), and the hook walks its own ancestry the same way, so the session pid is in both lists. The hook cannot name the attachment by session id because the documentation exports no session identity to MCP servers (only `CLAUDE_PROJECT_DIR`, `CLAUDE_PLUGIN_ROOT`, and `CLAUDE_PLUGIN_DATA`; manifest-reference "Where each variable resolves"), so process ancestry is the shared fact; it is best effort and documented as such. When none of the three fires (SIGKILL of everything at once, or a wrapper that hides the ancestry), the lease expires as today. The end is recorded durably in the store before anything is released and the release happens in the next tick's reconcile, so a crash between the two converges, and the hook returns within its budget: SessionEnd hooks share a 1.5 s budget that plugin-provided timeouts cannot raise (hooks reference, "SessionEnd"), so the hook does one `ps` walk and parallel loopback posts with short timeouts and never waits for the release.

A session that survives its own SessionEnd must re-attach. After `/clear` or a `/resume` switch the hook has ended the attachment while the session process and its MCP server keep running, and the server does not know. So the server sends its attachment id in the `x-orch-attachment` header of every request it forwards; when the id is not a live attachment the daemon still performs the operation and adds the response header `x-orch-attachment: unknown`; the server re-registers on seeing it. The operation is not retried, because it has been applied and most operator routes are not idempotent (`answer`, `nudge`, `ack`); the attachment only matters for liveness and for claims, and for claims the server re-registers before forwarding every `claim`, so a claim never carries a dead attachment. Rejected: refusing the operation with 409 until the server re-attaches, which adds a failure path to every route for the sake of one stale attachment that affects nothing but the next claim. Rejected: a `SessionEnd` signal for the idle clock. The window must exist anyway (a killed terminal fires no hook; the documentation covers SIGTERM only for `claude -p`), several sessions may be attached, and the attachment end already tells the daemon everything the signal would; so the idle clock has no hook of its own.

**Packaging: a committed launcher resolves the package; a checkout runs in place, a marketplace install runs the plugin-local copy that Claude Code installs from the plugin's own `package.json`, and `npx` is the fallback.** Facts verified against the Claude Code documentation on 2026-10-13 (URLs as cited):
- `${CLAUDE_PLUGIN_ROOT}` is substituted in `command`, `args`, and `env` of a plugin's stdio MCP servers and resolves to the plugin's installed directory: the cache copy for a marketplace install, the source directory for `--plugin-dir`; it is also exported as an environment variable to stdio MCP servers and to hook processes, and it changes when the plugin updates (plugins/manifest-reference "Environment variables" and "Where each variable resolves"; plugins/components "MCP servers" and "Hooks"; mcp "Plugin-provided MCP servers"). Official plugins use it in `args` (`bun run --cwd ${CLAUDE_PLUGIN_ROOT}`) and in hook commands.
- A marketplace entry with a relative `source` resolves from the marketplace root, so `./hosts/claude-code` is `<repo>/hosts/claude-code`; `claude plugin marketplace add owner/repo` clones the repository to `~/.claude/plugins/marketplaces/<name>/`, and the install copies the plugin directory alone into `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`: "Files outside the plugin directory aren't copied, so when a script inside a copied plugin reads a path above the plugin root, such as `../shared`, it doesn't find them" (plugins/loading "In-place and copied plugins"; plugins/marketplace-reference "Relative path plugin source"). `--plugin-dir` loads in place and is never copied (same section). The owner's cache confirms it: `cache/orchestrator/orchestrator/0.1.0/` holds `.mcp.json`, `.claude-plugin/`, `skills/`, and `workflows/` only.
- The automatic dependency install (plugins/loading "Node.js package dependencies", "When the dependency install runs", "Limits on the dependency install", "When the dependency install fails or is skipped"; re-read in full on 2026-10-13): "When Claude Code copies a plugin into the cache, it also installs the plugin's Node.js package dependencies there, so the plugin's hooks and MCP servers can load them." It runs "into the copied version directory each time it creates one": at install, at an update to a new version, and at session start when an enabled plugin is not cached yet. "The install runs only when the plugin's root directory contains both a `package.json` and a supported lockfile": `bun.lock`, `npm-shrinkwrap.json`, or `package-lock.json` (npm lockfile version 2 or 3), checked in that order, and npm is run "from the user's PATH". It never runs for in-place loads: `--plugin-dir` plugins "load in place and are never copied", and for a relative-path plugin from a local-path marketplace "Claude Code doesn't install the dependencies into the source directory". Limits: "every dependency must be a registry package pinned in the lockfile to an exact version"; "the install uses exactly the versions the lockfile pins, and Claude Code skips it when `package.json` and the lockfile don't list the same dependencies"; `--ignore-scripts`, so "dependencies that build native modules in those scripts download but don't compile"; a "60-second timeout"; it runs in a separate folder and "When the install succeeds, Claude Code moves the resulting `node_modules` into the plugin", so the tree lands at `${CLAUDE_PLUGIN_ROOT}/node_modules`; "You can't turn the automatic install off." On failure or skip "the plugin still loads, but the parts of it that need the missing packages may not work", `/plugin` and `claude plugin list` show a note, and a user-started update "can still retry an unfinished dependency install in that copy". A previous version directory is removed "in a background cleanup 14 days later" after an update orphans it (plugins/loading "Cleanup of previous versions").
- Hook events include `SessionStart` (matchers `startup`, `resume`, `clear`, `compact`, `fork`; plain stdout becomes context the model sees) and `SessionEnd` (reasons `clear`, `resume`, `logout`, `prompt_input_exit`, `other`; no decision control; a 1.5 s default budget that plugin-provided timeouts do not raise, overridable only by the user through `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS`). A plugin declares hooks in `hooks/hooks.json` under a top-level `hooks` key in the settings shape, or inline in `plugin.json`, and `${CLAUDE_PLUGIN_ROOT}` in a shell-form command must be quoted or `validate` warns (hooks "Hook lifecycle", "Matcher patterns", "SessionStart", "SessionEnd"; plugins/components "Hooks"; plugins/manifest-reference "hooks" and "Quoting and path separators"). `SessionStart` hooks at launch run before MCP servers are available, which rules out `mcp_tool` hooks for the report but not a command hook.
- Plugin stdio MCP servers are connected at session startup and run alongside the session; their teardown at session end is not documented, nor is any plugin service or daemon concept; the only background process a plugin can declare is a monitor, which "stop[s] when the session ends" and never starts under `-p` (mcp "Plugin-provided MCP servers", "Automatic lifecycle"; plugins/components "Monitors"; plugins/manifest-reference "monitors"). Nothing documents a PATH rule for MCP commands; the examples are `node ${CLAUDE_PLUGIN_ROOT}/server.js` and a binary under the plugin root (plugins/components "MCP servers").
- `claude plugin validate --strict` checks the manifest and each MCP server entry in `.mcp.json` (Claude Code 2.1.281 or later; the owner runs 2.1.296), reports invalid JSON in `hooks/hooks.json`, and treats warnings such as unrecognised manifest fields as errors (plugins/manifest-reference "Validate the manifest"; plugins/cli-reference "plugin validate").

Given those facts, and a dependency tree with no native module after `replace-sqlite-driver`: the published package is `@autodidacticon/orchestrator`, settled with the owner on 2026-10-13 (the scope is the owner's npm account, and both are free on the registry); `<name>` below stands for it. `.mcp.json` becomes `{ "command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/bin/orchestrator.mjs", "mcp"], "timeout": 180000 }`. The plugin directory carries `package.json`, a private manifest named for the plugin and not the orchestrator package (`{ "name": "orchestrator-claude-code-plugin", "private": true, "dependencies": { "@autodidacticon/orchestrator": "<version>" } }`, the version exact with no caret and equal to `.claude-plugin/plugin.json`), together with a committed `package-lock.json` (lockfile version 3) that resolves it, so that a marketplace install, an update, and a first session on a new machine trigger the automatic install and the package lands at `${CLAUDE_PLUGIN_ROOT}/node_modules/<name>/` with its pure-JavaScript dependencies beside it. The launcher is a dependency-free ESM script that locates itself with `import.meta.url` (so it works whether or not the variable is set), takes `mcp`, `ctl`, `daemon`, or `shim` as its first argument, and resolves the package in this order: (a) a checkout, recognised when `<plugin>/../../package.json` names the package, running `dist/src/<entry>.js` when built and otherwise `src/<entry>.ts` through `node_modules/tsx/dist/loader.mjs`, exactly as `daemonCommand()` and `shimCommand()` already fall back; (b) the plugin-local copy, `<plugin>/node_modules/<name>/dist/src/<entry>.js`, when that file exists; (c) the published package, `npx --yes --package=<name>@<version> <bin> …` with the `npx` beside `process.execPath` and the version read from `.claude-plugin/plugin.json`, when the plugin-local tree is missing or incomplete because the install was skipped, timed out, or was pruned. Before spawning, it compares `process.versions.node` with the package's `engines.node` floor (22.13.0 after `replace-sqlite-driver`, read from the resolved package's manifest) and fails with one readable line when the running Node is older, because `node:sqlite` would otherwise fail deep inside the daemon with `ERR_UNKNOWN_BUILTIN_MODULE`. It spawns the resolved command with inherited stdio, forwards `SIGTERM`, `SIGINT`, and `SIGHUP`, and exits with the child's code; `ORCH_LAUNCHER_DRY_RUN=1` prints `{ source: "checkout" | "plugin" | "npx", command, args }` instead, for tests. The daemon then resolves as today: `daemonCommand()` finds `dist/src/main.js` beside `lifecycle.js` in whichever tree the server runs from, the checkout, `${CLAUDE_PLUGIN_ROOT}/node_modules/<name>/`, or `~/.npm/_npx/<hash>/node_modules/<name>/`, and spawns it with the same `process.execPath`; the shim resolves the same way; nothing consults PATH, and a server started from the plugin-local tree spawns its daemon from that tree. In a checkout the plugin-local tree is never consulted (source (a) wins) and `hosts/claude-code/node_modules` is ignored by git. Rejected: vendoring the compiled package into `hosts/claude-code/server/` at build time; a marketplace install copies the git tree, so the vendored `dist` and `node_modules` would have to be committed. Rejected: `npx` as the primary path now that the automatic install can complete; it needs the registry at server start on every new machine and adds a few hundred milliseconds to each start, whereas the automatic install runs once at install time and its tree is loaded like any other plugin file; `npx` stays as the fallback because the install is best effort (sixty seconds, skipped when npm is missing from PATH or the lockfile disagrees with the manifest, and the version directory can be swept). Rejected: a `SessionStart` hook that installs into `${CLAUDE_PLUGIN_DATA}` with scripts enabled; the MCP server starts at session launch before hooks have run, so the first session fails, and with no native module there is nothing a scripted install adds. Rejected: `node ${CLAUDE_PLUGIN_ROOT}/../../dist/...` alone; it is exactly what a marketplace install cannot find. Rejected: a second, development-only plugin directory with its own `.mcp.json`; one launcher serves every case and keeps the skills and hooks in one place.

**The session start hook reads files and probes; it loads no package code.** For each `ORCH_HOME/runs/*` it reads `repo`, `daemon.pid`, and `daemon.json`; an alive pid is probed with `GET /v1/status?probe=1` (one-second timeout) and reported with its running, waiting, parked, attached, awaiting-review, and open-question counts; a dead pid with an exit record is reported only when the record's digest shows parked launches, open questions, a milestone awaiting review, or a stall; a dead pid with no record is reported as not stopped cleanly. One line, nothing when nothing qualifies, exit 0 always, ten-second timeout. Rejected: running `orchestrator-ctl runs` through the launcher from the hook; under `npx` with a cold cache that is a registry download at session start, and opening every store needs the native module, whereas the files answer the question in milliseconds whatever the install mode. The brief's "store has live work" is approximated by the exit record: an idle exit implies no live work, and a crash is reported regardless and recovered by the next revival.

**Hook contents.** `hosts/claude-code/hooks/hooks.json`:

```json
{
  "description": "Orchestrator: report runs at session start; release this session's worker launches at session end",
  "hooks": {
    "SessionStart": [
      { "matcher": "startup|resume|clear",
        "hooks": [ { "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/session-start.mjs\"", "timeout": 10 } ] }
    ],
    "SessionEnd": [
      { "hooks": [ { "type": "command", "command": "node \"${CLAUDE_PLUGIN_ROOT}/hooks/session-end.mjs\"" } ] }
    ]
  }
}
```

`session-end.mjs` reads the hook JSON from stdin for `reason`, collects its ancestor pids (`process.ppid`, then `ps -o ppid=` up to six levels, capped at 300 ms), and posts `{ pids, reason }` to `POST /v1/attachments/ended` of every alive daemon under `ORCH_HOME` in parallel with 400 ms timeouts; it exits 0 whatever happens. `session-start.mjs` prints, for example: `orchestrator: 2 runs under ~/.orchestrator need attention: /Users/r/app (daemon alive, 1 session attached, running T2, MVP awaiting review); /Users/r/lib (daemon exited idle 42 min ago: 2 launches parked, 1 open question). Use the run skill in that repository to continue.`

## Risks / Trade-offs

- [The daemon exits while a terminal user is still writing the graph] → the window is ten minutes and configurable, `orchestrator-ctl` revives on the next command after an idle exit, and the README says so.
- [Revival spawns a crash-looping daemon on every tool call] → `startDaemon` already fails with the log tail after twenty seconds; the error is visible, and `stop` or a signal records an explicit exit that stops the revival.
- [The automatic dependency install is capped at sixty seconds, is skipped when npm is missing from PATH or the lockfile and `package.json` disagree, and runs with no scripts] → the launcher falls back to `npx` whenever `${CLAUDE_PLUGIN_ROOT}/node_modules/<name>/dist` is missing, `claude plugin list` shows the install note, a user-started update retries the install, and the lockfile is regenerated with the pin at each release; the tree is pure JavaScript after `replace-sqlite-driver`, so no script is needed.
- [On the `npx` fallback a cold start needs the registry] → it pays once per version; the launcher reports the failure on stderr, where Claude Code shows MCP startup errors; a checkout and a completed plugin-local install never use `npx`.
- [The published version lags the plugin manifest] → the host test ties the three versions, and the release order in the migration plan publishes before pushing the bump.
- [On the `npx` fallback the daemon and the per-launch shim run from the npx cache tree (`~/.npm/_npx/<hash>/...`), which npm may prune while a daemon is alive, and on the plugin-local path from a plugin version directory, which Claude Code removes fourteen days after an update orphans it; a removed tree breaks the daemon's later dynamic imports (`recovery.js` at start, the MCP SDK in the server) and every new shim spawn until the daemon is revived from a fresh tree] → revival re-resolves the tree through the launcher, so the next tool call after a failure recovers; idle exit makes a daemon older than fourteen days unlikely; the checkout path never has the problem.
- [Process ancestry does not reach the MCP server (a wrapper or sandbox between them)] → the hook is best effort; the transport close and the pid check catch session death, and the lease catches everything else, as today.
- [The SessionEnd budget of 1.5 s is shared with other plugins' hooks] → the hook never waits for the release, only for the record, and times out silently.
- [A WIP commit lands on the launch branch] → the branch is the launch's own and is never published without a submit; the next brief names the commit so the agent can squash it.
- [Attachments keep a daemon alive while a session sits idle for hours] → that is the MCP server's lifetime too; `daemon.exitWhileAttached: true` restores the request-only rule.
- [Pull by default surprises a session that expected headless agents] → the `run` skill says who is working and offers `mode: spawn`; config and `start` with `mode` are explicit overrides.
- [Session workers run with the session's permissions] → that is the point; the allowed-tools list matters only for spawned agents and is the sibling change's job.

## Migration Plan

1. Land the code with `daemon.idleExitMs` defaulting to ten minutes; the crash suite and the slices run well inside it.
2. Rename the package to `@autodidacticon/orchestrator`, remove `private`, add `publishConfig` and `prepublishOnly`, and bump the version in `package.json`, `hosts/claude-code/.claude-plugin/plugin.json`, and the pin in `hosts/claude-code/package.json` together.
3. Publish to npm first (`npm publish` runs the build), then regenerate `hosts/claude-code/package-lock.json` against the published version (`npm install --package-lock-only` in the plugin directory; the lockfile must list exactly the manifest's dependency or the automatic install is skipped), then push the bump and the lockfile to the default branch; the marketplace installs from the branch and both the automatic install and the `npx` fallback pin the manifest version, so the package must exist before the manifest names it.
4. Checkout users: `npm install && npm run build`, then `claude --plugin-dir hosts/claude-code`; `npm unlink` is optional and only the terminal CLI still benefits from a link. Marketplace users: `claude plugin update orchestrator@orchestrator`, then `/reload-plugins` or a new session.
5. Existing run directories need nothing: a missing exit record with a dead pid reads as a crash and is revived on demand; launches without an attachment stay lease-governed.
6. Rollback: `daemon.idleExitMs: 0` disables the exit, `runner.mode: spawn` in `orchestrator.yaml` restores headless agents for a repository, and the previous `.mcp.json` works again with `npm link`.
