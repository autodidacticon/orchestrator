## Why

The daemon has no end of its own. `start` spawns it detached and it runs until someone calls `stop`; on 2026-10-13 two daemons were alive on the owner's machine (pids 36725 and 75375, both running `dist/src/main.js` from the checkout), one for a run that had finished over an hour earlier, and nothing in a Claude Code session says they exist. That sits outside plugin norms: a plugin's MCP server is a child of the session, but a process that outlives the session has no manifest field, no lifecycle hook, and no notice to the user. The plugin is also not self-contained: `hosts/claude-code/.mcp.json` runs `orchestrator-mcp` from PATH, so the plugin only works after `npm link` or a global install, and a marketplace install copies the `hosts/claude-code` subtree alone, with no package behind it (verified in `~/.claude/plugins/cache/orchestrator/orchestrator/0.1.0/`, which holds only `.mcp.json`, the skills, and the workflow). The PATH-dependent symlink bug fixed today in `src/entry.ts` was a direct consequence.

The owner also wants the default experience to be the one Claude Code already shows: tasks executed by visible, in-session subagents, not by hidden headless `claude -p` processes. The mechanism exists (runner mode `pull`, the `work` skill, and the bundled workflow `workflows/work.js`, which passed `test/e2e/work.test.ts` today with two workers), but `spawn` is the default and `work` is a separate skill the user must ask for. With `pull` as the plugin's default the daemon spawns no agent processes at all: it prepares worktrees and briefs, verifies and integrates on the rebased tree, and, with the idle exit added here, exits when nothing is left to do and no session is attached. The daemon becomes a short-lived coordinator rather than a background service, which is what "runs seamlessly within the Claude Code ecosystem" means for this project.

## What Changes

- Add `daemon.idleExitMs` (default ten minutes, 0 disables) and `daemon.exitWhileAttached` (default false). The daemon exits on its own, as a graceful stop, once it has been quiescent for the window: no launch preparing, launching, or live; no parked launch that a tick will still spawn (parked launches in `pull` mode are durable and do not count); no verifier job queued, in flight, or awaiting application; no pending cascade; no operator or agent request in flight or within the window, where an open `events` long-poll is a request in flight and liveness probes (`GET /v1/status?probe=1`) do not count; and no session attached unless `exitWhileAttached` is set. Pending tracker effects, an unfinished graph, a blocked question, and a milestone awaiting review do not keep it alive; they are durable.
- Record why the daemon exited. `daemon.json` gains `exit: { at, reason, reap, digest }` on every graceful exit (`idle`, `stop`, or `signal`); a dead pid with no record means a crash. `runs` (tool and CLI) reports it for every run whose daemon is not alive, and `status` reports `idle: { quiescent, idleMs, exitAfterMs }` and `attachments`.
- Revive on demand. The operator MCP server and the CLI start the daemon themselves when the run directory holds a store and the last exit was `idle` or a crash, so a session coming back after an idle exit sees no difference; after an explicit `stop` or a signal they keep refusing with the current error naming `start`. A fresh repository with no run directory still needs `start`.
- Session attachments. The operator MCP server registers itself with the daemon as an attachment `{ id, pids }`, its own pid followed by its ancestor chain, on first contact; it sends the attachment id with every request, re-registers whenever a response flags the attachment as unknown and before every `claim`, and ends it when its transport closes; claims made through it carry the attachment. The daemon ends an attachment whose process is dead at reconcile, and the plugin's `SessionEnd` hook ends every attachment whose chain contains a pid of the session that is ending. An ended attachment's held launches are released with `keep` on the next tick, so a worker subagent that dies with its session loses no work and, up to `daemon.maxKeptReleases` interruptions per task (default 3), costs no attempt.
- Kept release. `release` gains `keep`: with progress, uncommitted changes are committed on the launch branch as a work-in-progress commit, the branch is kept, the task returns to `unstarted` with `attempts` unchanged, and the next brief carries an `interrupted` context naming the branch and head so the relaunch continues from it; without progress it behaves as today; while `waiting` the task becomes `blocked` with its question and the same context. The overlay entry counts `interruptions`, reset when the task submits and reported in the brief and in `status`; past `daemon.maxKeptReleases` a kept release is a failed attempt as today. The worker-initiated release without `keep` keeps today's semantics.
- Pull is the plugin's default. The `start` tool, when it spawns the daemon without an explicit `mode`, applies `pull` as the run's durable mode unless the repository's `orchestrator.yaml` sets `runner.mode`; `orchestrator-ctl start` and the core default stay `spawn`. The `run` skill starts the daemon, and when the mode in force is `pull` or `mixed` runs the bundled workflow with a worker count bounded by capacity, then monitors; `work` remains the explicit way to add workers or switch modes.
- Make the plugin self-contained. `.mcp.json` runs `node ${CLAUDE_PLUGIN_ROOT}/bin/orchestrator.mjs mcp`, a dependency-free launcher committed with the plugin that runs the package from the repository checkout when the plugin directory sits inside one, otherwise from the plugin-local copy under `${CLAUDE_PLUGIN_ROOT}/node_modules` that Claude Code's automatic dependency install places there at marketplace install, and otherwise from the published npm package pinned to the plugin manifest's version through `npx`. The plugin directory carries a private `package.json`, named for the plugin, whose only dependency is the published package at the exact manifest version, plus a committed `package-lock.json`, which is what triggers the automatic install (registry packages only, no scripts, sixty seconds); it succeeds because, after `replace-sqlite-driver`, the dependency tree is pure JavaScript. The daemon is spawned from whichever tree the MCP server runs from, as today. Nothing in the plugin references an executable by name on PATH.
- Publish the package as `@autodidacticon/orchestrator` (settled with the owner on 2026-10-13; name and scope are free on the registry). `package.json` loses `private`, takes that name, which the launcher pins, and gains `prepublishOnly: npm run build` and `publishConfig.access: public`; the plugin manifest version, the package version, the launcher's package name, and the plugin's pin and lockfile are asserted in lockstep by a host test.
- Add plugin hooks: `hooks/hooks.json` with a `SessionStart` hook (`startup`, `resume`, `clear`) that prints one line naming every run under `ORCH_HOME` whose daemon is alive or whose last exit record shows work for a session or a human, and a `SessionEnd` hook that tells every alive daemon which session ended. Both read files and talk to loopback only; neither loads package code, so they run within the hook budgets whatever the install mode.
- Update the `run` and `work` skills and the README: visible workers by default, the daemon comes and goes on its own, nothing needs to be on PATH, and `npm link` is only for people who want `orchestrator-ctl` in a terminal.

## Capabilities

### New Capabilities

None. Idle exit, exit records, revival, and attachments belong to the daemon lifecycle that `operator-control` already specifies; packaging, the hooks, and the skills belong to `host-integration`; the kept release extends `pull-runner`, `task-lifecycle`, and `agent-protocol`.

### Modified Capabilities

- `operator-control`: adds the idle exit rule, the exit record with its `runs` and `status` facts, revival on demand, and session attachments; modifies the daemon lifecycle, run directory, and claims-and-releases requirements.
- `operator-mcp`: the "daemon not running" behaviour changes from always refusing to reviving after an idle exit or crash and refusing only after an explicit stop; the server registers an attachment and ends it on close; `start` applies the plugin's `pull` default; `release` takes `keep`.
- `host-integration`: the per-host wrapper no longer references executables by name; the plugin carries a launcher and `SessionStart` and `SessionEnd` hooks; the marketplace install is self-contained through the published package; the `run` skill runs the workflow in pull mode and the skills stop asking for PATH.
- `pull-runner`: `release` with `keep`; session attachments on claims and the release of an ended attachment's launches.
- `task-lifecycle`: the `running -> unstarted` row also covers a kept release after progress; `attempts` does not increase on a kept release.
- `agent-protocol`: the `interrupted` context in the brief.
- `crash-recovery`: an idle exit is a graceful stop with nothing to adopt, a revived daemon finds durable state and nothing to do, and an attachment end is a durable record applied by the next tick, before or after a crash.

## Impact

- `src/config.ts` gains `daemon.idleExitMs`, `daemon.exitWhileAttached`, and `daemon.maxKeptReleases`. `src/loop/orchestrator.ts` gains `quiescent()`, request accounting (`requestBegan`, `requestEnded`), attachments (`attach`, `endAttachment`, `endAttachmentsByPids`, `attachments()`), `idleMs()`, `idleExitDue()`, the `idle` and `attachments` fields of `StatusReport`, `release` with `keep` and the `interruptions` bound, and the idle check after each loop iteration. `src/loop/tick.ts` reconcile ends dead or ended attachments and releases their launches. `src/agent/server.ts` counts requests, recognises `probe=1`, and flags an unknown `x-orch-attachment`. `src/main.ts` writes the exit record, accepts `--default-mode`, and passes the exit reason. `src/runs/runDir.ts` and `src/runs/lifecycle.ts` gain the exit record type, `daemonState().exit`, `listRuns()[].exit`, and `reviveDaemon()`; new `src/runs/ancestry.ts` walks a process's ancestor chain. `src/operator/routes.ts` gains the attachment routes and `keep` on release. `src/operator/mcp-server.ts` revives on demand, registers its attachment with its ancestor chain, re-registers when flagged unknown and before claims, ends it on close, applies the `pull` default on spawn, and exposes `keep`. `src/operator/cli.ts` revives on demand and takes `--keep`. `src/workspace/workspace.ts` gains `preserve(launch)` (git and fake). `src/brief/compose.ts` renders the `interrupted` context. `src/state/status.ts` gains `InterruptedContext` and `Entry.interruptions`; `src/state/store.ts` `Launch.worker` gains `attachment`.
- Prerequisite: this change is applied after `replace-sqlite-driver`, which replaces `better-sqlite3` with `node:sqlite`; the plugin-local install path assumes a dependency tree with no native module. Until it lands, the launcher's checkout and `npx` paths work as before and the plugin-local path is simply never chosen, because the install cannot complete.
- New plugin files: `hosts/claude-code/bin/orchestrator.mjs`, `hosts/claude-code/package.json` (private, named for the plugin, one exact dependency), `hosts/claude-code/package-lock.json`, `hosts/claude-code/hooks/hooks.json`, `hosts/claude-code/hooks/session-start.mjs`, `hosts/claude-code/hooks/session-end.mjs`. Changed: `hosts/claude-code/.mcp.json`, `skills/run/SKILL.md`, `skills/work/SKILL.md`, `.gitignore` (the plugin's `node_modules`).
- `package.json`: name, `private`, `publishConfig`, `prepublishOnly`, version lockstep with `hosts/claude-code/.claude-plugin/plugin.json` and the plugin's pin. A release publishes to npm first, regenerates the plugin lockfile against the published version, and only then pushes the bump to the default branch, because the marketplace installs from the branch, the automatic install is frozen to the lockfile, and the launcher's `npx` fallback pins the manifest version.
- Tests: `test/loop/idle.test.ts` (new), `test/slice/idle.test.ts` (new), `test/loop/scenarios.test.ts`, `test/loop/brief.test.ts`, `test/slice/claim.test.ts`, `test/runs/lifecycle.test.ts`, `test/slice/operator-mcp.test.ts`, `test/host/package.test.ts`, `test/e2e/plugin.test.ts` and `test/e2e/work.test.ts` (both drop the PATH wrapper; the plugin e2e becomes the default-experience test). The crash suite is unchanged and keeps passing with the default window.
- Migration: people who used `npm link` for the plugin can unlink; `claude --plugin-dir hosts/claude-code` works after `npm install && npm run build` with nothing on PATH, and `npm link` remains only for the terminal CLI. Runs started before this change keep working: a `daemon.json` without `exit` and a dead pid is treated as a crash and revived on the next tool call, and launches without an attachment are governed by their leases as today. Runs that relied on the daemon spawning agents from a session set `runner.mode: spawn` in `orchestrator.yaml` or pass `mode` to `start`. Foreground users who want a daemon that never exits set `daemon.idleExitMs: 0`.
- Session subagents run under the session's own permissions and login, so the allowed-tools problem for spawned agents, which the sibling change `add-toolchain-discovery` solves, applies only to `spawn` and `mixed` modes. Related open item, out of scope: reconcile reaps an agent as soon as its report clears the lease, losing the final usage JSON and the tail of its log.
