## Context

`SqliteStore` in `src/state/sqlite.ts` implements the `Store` interface of `src/state/store.ts` over one `better-sqlite3` connection: WAL journal, `synchronous = NORMAL`, 37 `prepare` sites with positional `?` parameters, `run` (16), `get` (15), `all` (6), two `pragma` calls, one `exec` for the schema, one `transaction`, one `close`. The daemon (`src/main.ts`) and `orchestrator-ctl` under `--data-dir` (`resolveUrl` in `src/operator/cli.ts`) open it; the operator MCP server and the agent shim never load it; the core library exports it. Every harness (`test/loop`, `test/slice`, `test/crash`, `test/runs`, `test/e2e`) opens the same file, the crash and lifecycle harnesses from a second process while the daemon writes. `better-sqlite3` is the only native module among the 131 production packages in the lockfile: it alone carries `hasInstallScript` and a `binding.gyp`, and it brings 34 transitive packages (`prebuild-install`, `tar-fs`, `node-abi`, and their trees) that nothing else uses.

Facts verified on this machine on 2026-10-13 (Node v22.23.2 with SQLite 3.51.3 bundled, `better-sqlite3` 12.11.1, `@types/node` 22.20.5):

- `better-sqlite3` defaults the busy timeout to 5000 ms (`lib/database.js`: `'timeout' in options ? options.timeout : 5000`); `node:sqlite` defaults to 0, so a second connection's write fails at once with `database is locked` unless `PRAGMA busy_timeout` is set. Foreign keys are on and double-quoted string literals off under both; the schema uses neither.
- `better-sqlite3`'s `db.transaction(fn)()` issues a deferred `BEGIN`, then `COMMIT` or `ROLLBACK`, and turns a transaction function called inside another into a savepoint. `node:sqlite` has no transaction helper and a nested `BEGIN` throws `cannot start a transaction within a transaction`. Nesting is pervasive, not incidental: `Orchestrator.transition()` opens its own transaction and is called inside `fail()`, inside `acceptSubmission()` (itself inside the report transaction), and inside `handleBlock`, `cancel`, `reopen`, `resetMilestone`, `acceptMilestone`, `rejectMilestone`, `unblock`, `release`, and `drainVerification` in `src/loop/tick.ts`; `queueNotice()` runs inside the publish transaction through `notifyBaseMoved`; `recordSignal()` in `src/health/progress.ts` runs inside the heartbeat transaction. An instrumented run of the in-process suites counted 597 nested calls, 71 of them two levels deep (`drainVerification` to `fail` to `transition`).
- Both drivers bind every JavaScript number as a REAL and rely on INTEGER column affinity to store integral values as INTEGER (`typeof(created_at)` reads `integer` after a round trip, and `WHERE seq = ?` finds its row); both return INTEGER columns as numbers; `run()` returns `{ changes, lastInsertRowid }` as numbers under both; `get()` returns `undefined` for no row under both; `INSERT OR IGNORE` reports `changes` 0 under both. Neither binds a boolean.
- Differences: `node:sqlite` returns rows as null-prototype objects (better-sqlite3: plain objects); throws `cannot be bound` on `undefined` (better-sqlite3 binds NULL); throws `ERR_INVALID_STATE` on a second `close()` (better-sqlite3: no-op); and throws a plain `Error` with `code` `ERR_SQLITE_ERROR`, `errcode` (the extended result code, 2067 for a UNIQUE violation), `errstr` (`constraint failed`), and the message SQLite gives both drivers (`UNIQUE constraint failed: launches.launch_id`), where better-sqlite3 throws `SqliteError` with `code` `SQLITE_CONSTRAINT_UNIQUE`. Nothing in `src/` or `test/` inspects a SQLite error's class, `code`, or `errcode`. The store never binds `undefined`: every nullable write coalesces with `?? null`, the nack route stringifies `error`, and the remaining bound values go to NOT NULL columns.
- Loading `node:sqlite` emits `ExperimentalWarning: SQLite is an experimental feature and might change at any time` once per process, delivered on `process.nextTick` to the `warning` listeners, of which Node's default printer is one (`process.listeners('warning')` is `[onWarning]`). Replacing the listeners with a filter that forwards everything but that warning works under CommonJS, Node ESM, tsx, and vitest's vite-node, whether the filter sits in a sibling module imported first or after the import in the same module body; a later `process.emitWarning('probe')` still prints. A one-shot variant that puts the original listeners back once the warning has been swallowed, with a `setImmediate` fallback for the case where it never arrives, is safe in all four runtimes when the fallback is armed after `node:sqlite` has evaluated: the listeners read back as the originals after one turn of the event loop and `probe` still prints. Armed at install time instead, the fallback leaks the warning under vite-node, which does file I/O between module bodies, so the check phase runs before the builtin evaluates (verified: the warning printed in a vitest fork). `--disable-warning=ExperimentalWarning` (Node 21.3+) also works, on the command line and in `NODE_OPTIONS`. All four executables print nothing to stderr on `--help` today, and `orchestrator-ctl --data-dir <empty> status` exits 2 with exactly one stderr line.
- `@types/node` 22.20.5 already ships `sqlite.d.ts` with `DatabaseSync`, `StatementSync`, and `SQLInputValue`; `database.isTransaction` and the constructor `timeout` option arrived in v22.16.0, after the floor.
- No spec names the driver, WAL, or SQLite; the archived v1 design record is the only mention. `openspec/config.yaml`'s context line names `better-sqlite3`.

Constraints: the `Store` interface and `SqliteStore`'s public surface stay as they are; no schema change; the crash suite and every harness run unchanged; `add-daemon-lifecycle` is applied after this change and its plugin-local packaging assumes the pure-JavaScript tree.

## Goals / Non-Goals

**Goals:**
- A production dependency tree with no native module, guarded by a test, so that an install with `--ignore-scripts` yields a working package.
- Identical store semantics: WAL, `synchronous = NORMAL`, the five-second busy timeout, deferred transactions with savepoint nesting, rollback on throw, `changes` and `lastInsertRowid` as numbers, `get` returning `undefined`, an existing `store.sqlite` opening unchanged.
- No ExperimentalWarning on a terminal, in an MCP log, or in the daemon log, however the process was started; no other warning hidden; the process's `warning` listeners back as they were within one turn of the event loop.
- No change to `daemonCommand()`, `shimCommand()`, the plugin, the bin shebangs, or the test configuration.

**Non-Goals:**
- A store abstraction over several drivers, or an asynchronous store.
- `BEGIN IMMEDIATE`, statement caching, or any other performance work.
- Node 24 or a stable `node:sqlite` API; the floor is the first release that loads it without a flag.
- A runtime Node-version check in the executables.

## Decisions

**`node:sqlite` behind the unchanged `Store` interface; the swap is confined to `src/state/sqlite.ts`.** The module imports `DatabaseSync` and `SQLInputValue` from `node:sqlite`; the constructor runs `PRAGMA journal_mode = WAL`, `PRAGMA synchronous = NORMAL`, `PRAGMA busy_timeout = 5000`, then the schema, all through `exec`. The 37 statements stay as written: positional `?` parameters only, so named-parameter prefixes and `setAllowBareNamedParameters` never arise; the argument arrays become `SQLInputValue[]`. The mapping, method by method: `new Database(path)` becomes `new DatabaseSync(path)`; `db.pragma('x = y')` becomes `db.exec('PRAGMA x = y')`; `db.exec(SCHEMA)` is unchanged; `db.prepare(sql).run(...)`, `.get(...)`, and `.all(...)` are unchanged in shape and result, and `Number(res.lastInsertRowid)` stays (a number already, a bigint only after `setReadBigInts`); `db.transaction(fn)()` becomes the wrapper below; `db.close()` is guarded by a `closed` flag so that a second close stays a no-op as before. `getSnapshot()` copies its row into `{ rev, content }` because it is the one row the store hands out unparsed and `node:sqlite` rows have a null prototype; every other method already builds new objects. A bound `undefined` is not normalised to NULL: the store never binds one, a caller that did would be writing a NOT NULL column, which throws under both drivers, and `cannot be bound` keeps the bug loud. Rejected: `run`/`get`/`all` helpers that coalesce `undefined`, which touch all 37 sites for a case that does not occur. Rejected: the constructor `timeout` option and `isTransaction`, both v22.16.0, because the pragma and a counter do the same work on every version at the floor.

**Transactions nest as savepoints, tracked by a depth counter.** At depth 0, `transaction(fn)` issues `BEGIN`, runs `fn`, issues `COMMIT`, and returns the value; on a throw it issues `ROLLBACK` and rethrows. At depth n above 0 it issues `SAVEPOINT orch_n`, runs `fn`, and `RELEASE orch_n`; on a throw it issues `ROLLBACK TO orch_n` then `RELEASE orch_n` and rethrows, so the inner function's writes are undone and the outer function decides whether to continue, exactly what better-sqlite3 did at the call sites listed in Context. The rollback statements run inside a try that ignores their own failure, because SQLite ends the transaction itself on `SQLITE_FULL`, `SQLITE_IOERR`, `SQLITE_NOMEM`, and `SQLITE_INTERRUPT`, and the original error is the one the caller must see; better-sqlite3 guards the same case with `inTransaction`. `BEGIN` stays deferred, matching better-sqlite3 and the daemon's single-writer design. A deferred transaction takes the write lock at its first write; the one failure that mode can produce under the busy timeout, `SQLITE_BUSY_SNAPSHOT`, arises only when another connection committed between this transaction's first read and its first write, which needs a second writer. No process other than the daemon writes the store today: `orchestrator-ctl` under `--data-dir` reads `apiBaseUrl`, and the crash, lifecycle, and end-to-end harnesses only read while a daemon runs. When a second writer appears, `BEGIN IMMEDIATE` at depth 0 is the one-line change, and the busy timeout then applies at `BEGIN`. Rejected: throwing on a nested call and unwrapping the callers, which means reworking `transition()` and sixteen callers for no behavioural gain, or splitting `transition()` into a transactional and a bare variant, which invites a transition recorded outside the transaction that holds its event. Rejected now: `BEGIN IMMEDIATE`, which changes lock acquisition for every daemon write to guard against a writer that does not exist.

**No error mapping layer; the contract is the message.** No code inspects SQLite error codes, so none is translated. What callers and tests may rely on becomes explicit: a primary key or unique violation throws an `Error` whose message names the constraint, identical under both drivers, and the enclosing transaction rolls back. `code` changes from `SQLITE_CONSTRAINT_UNIQUE` to `ERR_SQLITE_ERROR`, with the extended result code in `errcode` and SQLite's short text in `errstr`; the store header documents this for the next person who wants to branch on it. Rejected: a `StoreError` class with normalised codes, which adds public surface for no consumer and hides the message that names the constraint.

**The ExperimentalWarning is filtered in process by the store, once, and the process's listeners are put back within one turn of the event loop.** A side-effect module `src/state/sqlite-warning.ts`, imported by `src/state/sqlite.ts` before `node:sqlite`, takes the current `warning` listeners (Node's default printer, and anything an embedder installed earlier), removes them, and installs one listener that forwards every warning to them except a warning whose `name` is `ExperimentalWarning` and whose message mentions SQLite. The filter is one-shot: when it swallows that warning it removes itself and re-adds the original listeners, in their original order and ahead of any listener added meanwhile. If the warning never arrives, because the process loaded `node:sqlite` earlier or runs a Node that no longer warns, a fallback restores the listeners on the first `setImmediate` (`unref`'d) armed by `sqlite.ts` right after its imports, that is, after `node:sqlite` has evaluated and queued the warning on `process.nextTick`, which the check phase cannot overtake. The fallback is armed there and not at install time because vite-node performs file I/O between module bodies, so a fallback armed before the builtin evaluates fires first and leaks the warning into every vitest fork (verified). For an embedder importing the core library the side effect is therefore bounded: the listeners differ for at most one turn of the event loop, and `process.listeners('warning')` reads back as before once the store module has loaded. Importing the filter module first makes the order independent of when a loader evaluates the builtin; the warning is delivered on the next tick, after the module graph has evaluated, so even the same-module placement works, but the separate module is correct by construction. The effect is the same for the daemon spawned by `daemonCommand()` (whose stderr is `daemon.log`), `orchestrator-ctl` from a terminal, `npm run dev` under tsx, every vitest fork, the launcher that `add-daemon-lifecycle` introduces, and a user's own `.mcp.json`; the operator MCP server and the shim never load the store and were quiet already; `daemonCommand()`, `shimCommand()`, `vitest.config.ts`, and the shebangs stay as they are, and the lifecycle launcher has nothing to add. Rejected: `--disable-warning=ExperimentalWarning` on the spawned command lines. It is the documented mechanism, but it has to be repeated at every spawn point (`daemonCommand()`, `shimCommand()`, the launcher, vitest's `execArgv`, the `dev` script), leaves every direct invocation printing (`orchestrator-ctl` on every call from a terminal; `orchestrator-mcp` from a user-written `.mcp.json`, into the MCP log on every session start), and silences every ExperimentalWarning in those processes, not only SQLite's. Rejected: `#!/usr/bin/env -S node --disable-warning=ExperimentalWarning` in the four entrypoints; `env -S` is absent on coreutils before 8.30 and on some BusyBox builds, where the executable then fails to start at all, a worse failure than a warning line. Rejected: re-executing the process with the flag, which doubles every process, changes the pid `startDaemon` records and polls, and adds a startup to every MCP server. Rejected: `NODE_OPTIONS` in spawned environments, which every grandchild inherits, including the agents' Claude Code processes. Rejected: accepting the warning on stderr, so that every daemon log and MCP log opens with it. Rejected: a filter that stays for the life of the process, which is simpler but leaves a library's global side effect in place for every embedder of `src/index.ts`; the one-shot version costs a dozen lines. Trade-off accepted: the filter relies on Node's default printer being an ordinary `process` listener, which has been so since Node 6 but is not documented as a contract; tests run a real executable in a child process and assert a clean stderr and restored listeners, so a Node release that changes this fails the suite instead of degrading silently, and the documented flag is the fallback.

**The pure-JavaScript property is guarded in the host tests, from the lockfile.** `package-lock.json` (lockfile version 3) marks every package with an `install`, `preinstall`, or `postinstall` script as `hasInstallScript` and dev-only packages as `dev: true`; today the only production entry with the flag is `better-sqlite3` (`esbuild` and `fsevents` are dev). The test asserts that no non-dev entry carries `hasInstallScript`, that no non-dev package directory under `node_modules` contains `binding.gyp`, that `better-sqlite3` is absent from `dependencies` and `@types/better-sqlite3` from `devDependencies`, and that `engines.node` is `>=22.13.0`. Optional entries count as production because `npm install --omit=dev` installs them. Rejected: installing into a temp directory with `--ignore-scripts` inside the test, which needs the registry; the lockfile flag is the fact npm itself records. Rejected: trusting `engines` alone, which npm reports and does not enforce without `engine-strict`.

**`engines.node` becomes `>=22.13.0`.** The first release that loads `node:sqlite` without `--experimental-sqlite`. The README prerequisite moves from Node 22 to Node 22.13, and `openspec/config.yaml`'s context line names `node:sqlite`.

## Risks / Trade-offs

- [`node:sqlite` is Stability 1.1, active development] → the store uses six methods whose shapes have not changed since v22.5.0; `@types/node` catches a signature change at `npm run typecheck`; the suite catches a behavioural one; the floor pins the earliest unflagged release rather than tracking the newest.
- [Node's default warning printer stops being a removable listener, or the message loses the word SQLite] → the child-process stderr tests and the listener-restore test fail; the fallback is `--disable-warning=ExperimentalWarning` at the spawn points and in the shebangs.
- [`node:sqlite` benchmarks somewhat slower per statement than better-sqlite3] → both drivers prepare each statement per call here, the daemon writes a few rows per tick, and no path is bound by SQLite latency; the crash suite's timings are the check.
- [The bundled SQLite follows the Node release rather than the package] → the file format is compatible across SQLite 3.x; the schema uses no extension and no version-specific SQL.
- [Node 22.0 to 22.12 fails with `ERR_UNKNOWN_BUILTIN_MODULE` for `node:sqlite` rather than a friendly message] → `engines` warns at install, the README names the floor, and the launcher in `add-daemon-lifecycle` compares `process.versions.node` with the package's `engines` floor and prints one line before spawning; that check is adopted into that change's launcher requirement and is not designed here.
- [A second `close()` or a bound `undefined` behaves differently] → `close()` is made idempotent; a bound `undefined` throws `cannot be bound` where it threw a NOT NULL violation before, and no path binds one.
- [A nested transaction semantic a caller relied on without a test differs from better-sqlite3] → the wrapper reproduces its savepoint behaviour and two tests pin both directions; the full suite, with 597 nested calls in the in-process part alone, exercises the rest.
- [The production tree changes shape: 35 packages leave] → nothing imports them; `npm ls --omit=dev` and the host test confirm the result.

## Migration Plan

No schema change and no data migration. An existing `store.sqlite` opens unchanged: the DDL is `CREATE ... IF NOT EXISTS`, `journal_mode = WAL` is persisted in the file and re-issued as a no-op, and the `-wal` and `-shm` sidecars are SQLite's own. Rolling back is reverting `src/state/sqlite.ts` and reinstalling `better-sqlite3`; both drivers read the same file. `npm install` after the change removes `better-sqlite3` and 34 transitive packages from `node_modules` and the lockfile, taking the production tree from 131 packages to 96; CI and the verifier's temp roots stop compiling. `add-daemon-lifecycle` is applied after this change; its plugin-local packaging and its `npx` fallback both assume the pure-JavaScript tree, and its launcher needs no warning flag.
