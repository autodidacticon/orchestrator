## Why

Without an `orchestrator.yaml`, a run uses `checkCommand: npm test`, `integrationBranch: main`, and a runner command whose `--allowedTools` list names `Bash(git:*)` and the five orchestrator MCP tools and nothing else. In today's walkthrough (2026-10-13) the first throwaway repository had no config file: the agent finished its task, was denied every attempt to run `npm test`, `node --test`, and `node -e`, asked a `needsAccess` question, and sat for four and a half minutes until the operator answered "I ran it; it passes". The run looked hung. The second repository only worked because its `orchestrator.yaml` copied the whole default runner command and appended two tool rules. Users should not have to know the runner command to let agents run the project's tests, and should not need a config file at all for an ordinary repository. The owner's judgement: the toolchain is auto-discovered, `orchestrator.yaml` stays optional, and anything the daemon could not work out is said plainly and can be set from the session without a restart.

## What Changes

- Resolve every configurable value in one order: an explicit argument (the `start` tool, `orchestrator-ctl start`, or a daemon `--set key=value` flag), then `<repo>/orchestrator.yaml`, then detection from the repository, then the built-in default. Every resolved value records its provenance as `argument`, `file`, `pinned` (the integration branch a run first used), `detected`, or `default`; an unresolvable required value records `unresolved`.
- Detect the check command from the repository root at daemon start: a `Makefile` with a `test` target, then `package.json` with a real `scripts.test` run by the package manager the lockfile or `packageManager` field names, then `Cargo.toml`, `go.mod`, a Python project file (`uv run pytest` or `poetry run pytest` when their lockfiles exist), `Gemfile`, Gradle, Maven, `mix.exs`, and `.sln`/`.csproj`. The first match in that fixed order gives the check command; nothing matching leaves `checkCommand` unresolved. `npm test` is no longer assumed.
- Detect the integration branch: the branch `refs/remotes/origin/HEAD` points at when it exists locally, else the current branch, else `main`. The branch a run first used is pinned in the store and beats detection and the default on every later start, with provenance `pinned`, so a moved `origin/HEAD` or a feature branch checked out in the main checkout never changes a run's branch. Only an explicit argument or file value naming a different branch conflicts with the pin: it is refused while the run holds launches or jobs, and adopted and re-pinned when it holds neither.
- Derive the allowed tools of the agents the daemon spawns from every toolchain found in the repository root (for Node: the package manager's `test`, `run`, `install`, and `ci` subcommands, `npx`, and `node`; for the others their obvious counterparts), plus `Bash(git:*)` and the five orchestrator MCP tools, plus any rules the file or an argument adds. List-valued keys compose across layers rather than override; each rule records its source.
- Compose the runner command from a template: `DEFAULT_CLAUDE_COMMAND` gains an `{allowedTools}` slot that the Claude Code runner fills at every spawn, so a user extends the list with `runner.claude.allowedTools` or a `start` argument instead of copying the command. A `runnerCommand` without the slot is still used verbatim, as today.
- Scope the two halves by runner mode. Claimed launches run under the worker's own permissions in every mode, and session subagents need no allow list from the orchestrator. The daemon composes the list only for launches it spawns, which are all launches in `spawn` mode (what `orchestrator-ctl start` from a terminal keeps) and the ones nobody claimed within the window in `mixed` mode. The detected check command and integration branch apply in every mode because the verifier uses them. The sibling change `add-daemon-lifecycle` decides the plugin's default mode and the work workflow; this change designs neither.
- Hold verification while `checkCommand` is unresolved instead of running `npm test` blindly or failing the submission: the job stays `queued`, the sealed work is kept, `status` and the `wait` digest report `needsConfig: ['checkCommand']`, and the job runs on the first tick after a command is set. A declared no-op, whose sealed sha equals its base sha, never runs the check command and is verified and published at once. The brief tells the agent when no check command is configured yet.
- Record the resolved configuration with provenance in the run directory as `config.json` beside `daemon.json`, with the operator overrides themselves durable in the store, and report a `config` block with value and source per key, the detected `toolchain`, and `needsConfig` in `status` and in the `start` response.
- Add a configuration route, `GET /v1/config` and `PUT /v1/config`, the CLI command `orchestrator-ctl config`, the operator MCP tool `configure`, and the same keys as optional `start` arguments. `checkCommand`, `capacity`, `allowedTools`, and `runnerCommand` take effect for subsequent verifications and launches without a restart; `integrationBranch` is start-only. Every override is an operator event.
- Have the `run`, `import`, and `work` skills report the detected toolchain in one line after `start` and, when `checkCommand` is unresolved, find the test command in `CLAUDE.md`, the README, or the manifests, propose it, and set it through `configure`.

## Capabilities

### New Capabilities
- `toolchain-discovery`: the resolution order and provenance model, the detection table and its precedence, the unresolved outcome, integration branch detection and pinning, the derived allowed tools, runner command composition, the resolved configuration record, and the runtime override rules.

### Modified Capabilities
- `operator-control`: the operator interface gains `config`; new requirements for the configuration route, the configuration facts `status` and the digest report, and the `start` arguments.
- `operator-mcp`: the `start` tool takes configuration arguments and returns the config block; a new `configure` tool.
- `integration-pipeline`: the check step runs the effective check command and holds the job while it is unresolved.
- `agent-protocol`: the brief states the effective check command or that none is configured yet.
- `host-integration`: the skills report the toolchain and resolve an unresolved check command through the session.

## Impact

- New module `src/toolchain/detect.ts` (detection and the allowed-tools table) and `src/runs/resolve.ts` (layered resolution with provenance, `config.json`); `src/config.ts` makes `checkCommand` optional and adds `runner.claude.{allowedTools, deriveTools}`; `src/runs/runDir.ts` `resolveRunConfig` returns the resolved record; `src/main.ts` accepts `--set`, pins the integration branch, and feeds getters to the runner and verifier; `src/runner/claude-code.ts` composes the command per spawn; `src/verify/verifier.ts` reads the check command per job; `src/loop/orchestrator.ts` gains `effective()`, `setConfig()`, and the config facts in `StatusReport`; `src/loop/tick.ts` reads effective capacity and holds unresolved verification; `src/brief/compose.ts` handles a missing check command.
- Routes `GET /v1/config` and `PUT /v1/config`; CLI `orchestrator-ctl config`; MCP tool `configure` and new `start` arguments; `startDaemon` passes `--set` flags or calls the route. Events `config.resolved` and `operator.config`. Store kv `config.overrides` and `integrationBranch`. Run directory file `config.json`.
- Config keys: `checkCommand` loses its default; `runner.claude.allowedTools` and `runner.claude.deriveTools` are new; `runnerCommand` keeps its meaning and gains the `{allowedTools}` slot in its default.
- Migration: an existing `orchestrator.yaml` keeps working unchanged. A file that sets `checkCommand` and `integrationBranch` sees no detection for those keys; a file whose `runnerCommand` has no `{allowedTools}` slot runs verbatim and the derived list is reported as not applied. A repository with no file and no detectable toolchain now holds verification and says so instead of running `npm test`. Test harnesses that relied on the `npm test` default set `checkCommand` explicitly.
- Skills `hosts/claude-code/skills/{run,import,work}/SKILL.md`, the README configuration section, and new fixtures under `test/fixtures/toolchains/`.
