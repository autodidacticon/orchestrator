## Context

Configuration is one zod schema in `src/config.ts` with defaults, loaded by `resolveRunConfig` in `src/runs/runDir.ts` from `<repo>/orchestrator.yaml` when the file exists. `src/main.ts` feeds `config.checkCommand` to `GitVerifierBackend`, `config.integrationBranch` to the workspace and verifier, and `config.runnerCommand` to `ClaudeCodeRunner`, whose default command carries a fixed `--allowedTools` list of `Bash(git:*)` and the five orchestrator MCP tools. The one runtime override that exists, `runner.mode`, is a kv entry the daemon writes from `--mode` or `PUT /v1/runner` and reads through `effectiveMode()`. The 2026-10-13 walkthrough showed the consequence of fixed defaults in a repository without a file: an agent that could not run `npm test` spent four and a half minutes on a `needsAccess` question. Constraints: the run must never write into the repository; every operator action is an event; the daemon converges after a crash at any point; the sibling change `add-daemon-lifecycle` owns the plugin's default runner mode and the work workflow.

## Goals / Non-Goals

**Goals:**
- Run an ordinary repository with no `orchestrator.yaml`: detect the check command, the integration branch, and the tools agents may run.
- Make every resolved value explainable: where it came from, and when it could not be resolved, say so where the session will see it.
- Let the session or the operator fix a gap without a restart and without copying the runner command.
- Keep `orchestrator.yaml` working unchanged as an optional in-repo override.

**Non-Goals:**
- Monorepos: per-package check commands or detection below the repository root.
- Deciding the plugin's default runner mode or the work workflow (`add-daemon-lifecycle`).
- A general shell allow list for agents (`ls`, `cat`, `cd`); only toolchain commands are derived.
- Changing the agents' permission mode or sandboxing; `acceptEdits` stays.
- Running probes such as the test command itself to validate detection.

## Decisions

**Four layers in one order; scalars take the first layer, lists compose.** Resolution is `argument`, then `file`, then `detected`, then `default`, and every leaf records the layer that supplied it. `allowedTools` is the one list-valued key and composes across layers in that order, recording each rule's layer under `parts`, so a file or an argument adds a rule without restating the derived ones. `integrationBranch` has one more layer, `pinned`, between file and detected: the branch the run first used, which the decision below explains. Rejected: strict override for lists, because the motivating case is "let agents also run docker" and an override would force the user to copy the derived list to add one rule. Rejected: file over argument, because an argument is the session's explicit intent at this moment while the file is whatever was committed.

**Argument overrides are durable in the store, like `runner.mode`.** A `start` argument or a `--set` flag becomes an entry in the kv document `config.overrides` before resolution, and `PUT /v1/config` writes the same document. A restart without arguments therefore keeps the override, which is what a session expects after it set the check command once and the daemon later crashed. Null clears an override and the value falls back to the next layer. Rejected: process-lifetime arguments, because a crash restart would silently revert to detection and the held verification would reappear. Rejected: writing arguments into `orchestrator.yaml`, because the run never writes into the repository.

**Detection reads the repository root only, against a fixed table, and the first row with a command wins.** The table and its order:

| Order | Manifest in the root | Check command | Tools derived |
|---|---|---|---|
| 1 | `Makefile`, `GNUmakefile`, or `makefile` with a line matching `^test\s*:` | `make test` | `Bash(make:*)` |
| 2 | `package.json` with a real `scripts.test` | `<pm> test` | `Bash(<pm> test:*)`, `Bash(<pm> run:*)`, `Bash(<pm> install:*)`, `Bash(<pm> exec:*)`, `Bash(node:*)`; npm adds `Bash(npm ci:*)` and `Bash(npx:*)`; pnpm and yarn add `Bash(npx:*)`; bun adds `Bash(bunx:*)` |
| 3 | `Cargo.toml` | `cargo test` | `Bash(cargo:*)` |
| 4 | `go.mod` | `go test ./...` | `Bash(go:*)` |
| 5 | `pyproject.toml`, `setup.cfg`, or `pytest.ini` | `uv run pytest` with `uv.lock`, else `poetry run pytest` with `poetry.lock`, else `pytest` | `Bash(pytest:*)`, `Bash(python:*)`, `Bash(python3:*)`, `Bash(pip:*)`, plus `Bash(uv:*)` or `Bash(poetry:*)` |
| 6 | `Gemfile` | `bundle exec rspec` with `.rspec`, else `bundle exec rake test` | `Bash(bundle:*)`, `Bash(rake:*)`, `Bash(rspec:*)`, `Bash(ruby:*)` |
| 7 | `build.gradle` or `build.gradle.kts` | `./gradlew test` with `gradlew`, else `gradle test` | `Bash(./gradlew:*)`, `Bash(gradle:*)` |
| 8 | `pom.xml` | `./mvnw -q test` with `mvnw`, else `mvn -q test` | `Bash(mvn:*)`, `Bash(./mvnw:*)` |
| 9 | `mix.exs` | `mix test` | `Bash(mix:*)`, `Bash(elixir:*)` |
| 10 | `*.sln` or `*.csproj` | `dotnet test` | `Bash(dotnet:*)` |

A `package.json` whose `test` script is npm's placeholder (`echo "Error: no test specified" && exit 1`) supplies no command but still counts as a found toolchain. The package manager is the `packageManager` field's name when present, else `pnpm-lock.yaml`, `yarn.lock`, `bun.lock` or `bun.lockb`, else npm. Every row whose manifest is present contributes its tools, so a polyglot repository's agents may run every toolchain in it while the check command is the project's declared one. Each decision writes a reason line. The Makefile comes first because a root `test` target is the repository's own declaration of how it is checked and usually wraps several toolchains; language manifests are per-language and follow in a fixed order. Rejected: language manifests before the Makefile, because a polyglot repository would then check only one language. Rejected: scanning subdirectories, because choosing among several packages is monorepo policy and out of scope. Rejected: probing by running commands, because detection must be instant and side-effect free at every daemon start.

**An unresolved check command holds verification; it does not fail the submission.** This departs from the sketch, which had the verifier fail submissions with a clear reason until a command is set. A failure spends an attempt, relaunches the agent for an operator-side gap, and with `maxAttempts` 2 blocks the task after two submissions; the sealed work would be redone from scratch. Instead a `queued` job is not taken up while `checkCommand` is unresolved: the task stays `submitted`, the sealed sha is kept, and the job runs on the first tick after a command is set. A declared no-op, whose sealed sha equals its base sha, is not held: the verifier never reaches the check step for it, so it verifies and publishes at once. A `noChanges` submission that nevertheless carries commits is held like any other, because the verifier may still need the command for it. The condition is reported wherever the session looks: `needsConfig` in the `start` result, in `status`, and in the `wait` digest, and the `config.resolved` event records it. Rejected: failing the submission, for the cost above. Rejected: pausing admission, because agents can usefully start while the session reads `CLAUDE.md` and sets the command within seconds. Rejected: keeping `npm test` as the default, which is the wrong command for most repositories and the cause of today's confusion in the rest.

**The integration branch is `origin/HEAD`, else the current branch, else `main`, detected once and then pinned per run.** `refs/remotes/origin/HEAD` is what a clone records as the remote's default branch, and it wins when the branch exists locally; a repository without a remote uses the branch that is checked out; a detached head gets `main`. The daemon pins the branch it first used in the store, and on every later start the pin beats detection and the default silently, with provenance `pinned`, because `baselineHead`, every worktree's base, and foreign-commit detection are tied to it, and because what detection reads moves for reasons unrelated to the run: a remote re-points `origin/HEAD`, a developer checks out a feature branch in the main checkout. Only an explicit layer that names a different branch (a `start` argument, a `--set` flag, or `orchestrator.yaml`) conflicts with the pin: refused while the store holds launches or jobs, adopted and re-pinned with `baselineHead` when it holds neither. Rejected: refusing to start whenever the resolved branch differs from the pin, because detection alone would then wedge a run nobody reconfigured. Rejected: re-resolving freely on every start, because a changed `origin/HEAD` mid-run would make submitted work rebase onto a different branch without anyone deciding it.

**The orchestrator derives the toolchain rules itself; the project's settings files add to them, and a project deny wins.** The sketch assumed `claude -p` in the worktree already reads the project's `.claude/settings.json` permissions. Checked against the Claude Code documentation (settings, permissions, permission-modes, headless, cli-reference, worktrees pages at code.claude.com/docs, 2026-10-13): `.claude/settings.json` is read from the session's primary working directory with no parent fallback, so the worktree's committed copy is read; but its `permissions.allow` and `additionalDirectories` apply only after the workspace trust dialog, which a `claude -p` run never shows, and in an untrusted folder they are not used with a warning on stderr. Trust is keyed to the main checkout's root, and the documentation does not say whether a worktree of a trusted checkout counts under `-p`. `.claude/settings.local.json` is read from the git repository's main checkout root even in a worktree, and allow rules in that untracked file apply without the trust step. Deny and ask rules apply at once, and "if a tool is denied at any level, no other level can allow it", so a project deny beats `--allowedTools`. The documentation does not state whether `--allowedTools` unions with or replaces file allow rules; it describes them as parallel sources of approval. Conclusion: the orchestrator cannot rely on project settings for the toolchain rules and passes its derived list with `--allowedTools`, which adds a source of approval and leaves the project's deny rules in force; a user's local allow rules and a trusted project's allow rules extend it. Rejected: relying on project settings alone, which fails in every repository without them and in every untrusted one. Rejected: `--settings` with inline `permissions.allow` JSON, because it "overrides the same keys in your settings.json files" and whether it merges or replaces the project's allow list is undocumented. Rejected: `--permission-mode bypassPermissions`, which removes the visible allow list, skips protections on `.git` and `.claude`, and is refused when running as root.

**Rules use the documented prefix form and name subcommands, not whole package managers.** `Bash(npm run:*)` is documented as equivalent to `Bash(npm run *)`: a trailing wildcard that matches `npm run`, `npm run build`, and flags, with `:*` recognised only at the end of a pattern; a rule without a wildcard is exact. So `Bash(npm test:*)` covers `npm test` and `npm test -- --watch`. Every part of a compound command must match a rule independently, which is why the brief tells agents to run commands from the worktree root rather than `cd src && npm test`. The install and runner rules (`install`, `ci`, `npx`, `bunx`, `pip`, `uv`, `poetry`) are included on purpose so that an agent can add a dependency; that is a policy choice, listed under risks with its exposure and remedies. Rejected: `Bash(npm:*)` wholesale, because the owner's list is deliberately narrower and the file or an argument widens it in one line.

**The runner command is a template with an `{allowedTools}` slot, filled at spawn.** `DEFAULT_CLAUDE_COMMAND` keeps its shape and replaces the fixed list with `--allowedTools {allowedTools}`. The subprocess runner reads the command and the effective list at every spawn and substitutes the slot with each rule double-quoted; a rule containing a double quote, backslash, dollar sign, or backtick is refused at configuration time so the composed command is always well formed. A `runnerCommand` without the slot runs verbatim, as every existing file expects, and the configuration record marks the list as not applied. Rejected: a structured `runner.claude` block that generates the whole command, because the full template is the escape hatch for anything the block does not model (a different permission mode, a different executable). Rejected: separate base and extra keys, because `parts` already shows who contributed what.

**The derived list reaches only launches the daemon spawns; the check command and branch reach every mode.** In `spawn` mode, and in `mixed` mode once the claim window elapses, the daemon composes the command and the list applies. A claimed launch has no process of ours: the worker runs under its own permissions and login, so no list is composed for it and the claim response carries none. The verifier runs the check command on every submission whatever the mode, and the integration branch is where every mode publishes. `orchestrator-ctl start` from a terminal keeps `spawn`; `add-daemon-lifecycle` decides the plugin's default and the work workflow, and this change designs neither.

**Overrides live in the store; `config.json` is an informational mirror.** The override document is kv `config.overrides`, written in the same transaction as the `operator.config` event, so the durable truth and its audit record cannot disagree. The resolved configuration with provenance, the detection record, and `needsConfig` are written to `<runDir>/config.json` by temp file and rename at every start and after every accepted override, next to `daemon.json` and for the same reason: a human or the `runs` listing can read it while the daemon is down. `status` computes the same facts live and never reads the file. Rejected: the file as the source of truth, because it cannot be transactional with the event. Rejected: the store only, because nothing outside the daemon can read it and `daemon.json` already set the pattern.

**Runtime overrides apply to the next unit of work; `integrationBranch` is start-only.** `checkCommand` is read when a job starts checking and held for the job; `capacity` is read at each admission pass; `allowedTools` and `runnerCommand` are read at each spawn, so a launch already live keeps its flags. `integrationBranch` is accepted as a `start` argument that spawns the daemon, subject to pinning, and refused with 409 on a running daemon; a request mixing it with other keys applies nothing, so a caller never has to guess which half landed. Rejected: snapshotting the list per launch at preparation, because a parked launch spawned later should get the current list and the live process has its own flags anyway.

**A `configure` tool and route beside `start` arguments, not instead of them.** `start` needs the arguments: start-only keys can only be given there, and a session's first `start` is where it states what it knows. The route is needed regardless, because an argument on a running daemon has to reach it somehow, exactly as `mode` reaches `PUT /v1/runner`. The question was whether to expose the route as its own tool and CLI command. It is one tool and one command, and it buys a precise response (`applied`, `rejected`, the new block) and an honest verb for a mid-run change such as "agents may also run docker", which reads wrongly as a lifecycle operation. Rejected: `start` arguments only, because a mid-run change through `start` either returns daemon facts that hide what was applied or grows into the config route under another name. Rejected: folding `PUT /v1/runner` into the new route now; it is an open question.

**The session resolves what detection could not, with the user's confirmation when the documentation is ambiguous.** The `run`, `import`, and `work` skills report one line after `start`. On `needsConfig`, the skill reads `CLAUDE.md`, the README, and the root manifests; when the test command is stated unambiguously it sets it through `configure` and says where it found it, otherwise it proposes or asks and sets only what the user confirms. When a live agent asks `needsAccess` for a command, the skill offers a rule for later launches, says the live process cannot gain it, and offers to run the command itself and answer with the result, which is what the operator did by hand today. Rejected: always asking, because a `CLAUDE.md` that says "run tests with `make check`" leaves nothing to decide.

**`checkCommand` loses its default in the schema.** `Config['checkCommand']` becomes `string | undefined`, which makes every consumer handle the unresolved case at compile time: the brief says none is configured yet, the verifier holds, and the harnesses that relied on `npm test` set `'true'` explicitly. Rejected: a sentinel string such as `''`, which would reach `/bin/sh` somewhere eventually.

## Risks / Trade-offs

- [A root Makefile's `test` target does something heavy or environment-bound] → the reason line names the Makefile, the session reports the detected command before any agent runs, and one `configure` call or one file line overrides it.
- [A stale lockfile picks the wrong package manager] → the `packageManager` field wins when present; the reasons name the lockfile; override in one line.
- [`origin/HEAD` is re-pointed or a feature branch is checked out in the main checkout while a run is live] → the pin wins silently with provenance `pinned`, `status.config.integrationBranch` shows it, and only an explicit value can change it, which is refused until the run holds no launches or jobs.
- [The derived Node and Python rules include `Bash(npm install:*)`, `Bash(npm ci:*)`, `Bash(npx:*)`, `Bash(bunx:*)`, `Bash(pip:*)`, `Bash(uv:*)`, and `Bash(poetry:*)`, which let a spawned agent fetch and execute arbitrary packages, with their postinstall scripts, using the user's credentials and caches] → a deliberate default for a coding agent that may add a dependency, and the verifier already runs the project's own scripts; the remedies are one line each: `runner.claude.deriveTools: false` with an explicit `runner.claude.allowedTools`, or a project `deny` rule in `.claude/settings.json`, which wins over any allow list.
- [Project allow rules may not apply under `-p` because trust is never granted] → the derived list is the floor and does not depend on them; the opt-in e2e records whether the worktree inherited trust; the user's local file applies regardless.
- [Compound commands need every part allowed, so `cd x && npm test` is denied] → the brief says to run from the worktree root; helpers can be added through `runner.claude.allowedTools`; a shell floor is an open question.
- [A live process cannot gain a rule added mid-run] → stated in the skill, which offers to run the command and answer; later launches get the rule.
- [Held verification looks like a stall to someone who ignores `needsConfig`] → it is in the `start` result, `status`, and every digest, the task shows under `verifying`, and the skills act on it; the sealed work is never lost.
- [Detection runs once per start, so a manifest an agent adds mid-run is not seen] → a restart re-detects; `configure` sets it at once; an open question records automatic re-detection.
- [`checkCommand` becoming optional ripples through types] → compile errors guide every consumer; harnesses set it explicitly; the crash harness already writes it.
- [A repository with no manifest and no file now holds instead of running `npm test`] → that default was wrong for such a repository; the hold is reported and resolved from the session.
- [`config.json` written while the daemon dies] → temp file and rename; the store is the truth.

## Migration Plan

No store table changes: two kv entries (`config.overrides`, `integrationBranch`) and one run directory file (`config.json`). Existing `orchestrator.yaml` files keep working unchanged: keys they set resolve with source `file`, a `runnerCommand` without the slot runs verbatim, and a file that sets `checkCommand` and `integrationBranch` sees no detection for them. The default template changes only in replacing its fixed list with the slot; repositories that relied on the old fixed list get a superset. Runs that relied on the `npm test` default in a repository with a `package.json` test script get the same command by detection; a repository with nothing detectable now holds verification and reports `needsConfig` instead. `test/loop/harness.ts` sets `checkCommand: 'true'`; `test/slice/harness.ts` and the crash harness already do. The tool count in the operator MCP test rises by one. The README's configuration section is rewritten around "no file needed".

## Open Questions

- Whether spawned agents should get a configurable shell floor (`Bash(ls:*)`, `Bash(cat:*)`, `Bash(cd:*)`, and the like) beside the toolchain rules.
- Whether `PUT /v1/runner` and `runner.mode` should fold into `PUT /v1/config` and the `config` block with provenance.
- Whether detection should re-run when a reload or a publication adds a manifest to the repository root.
- Whether a worktree of a trusted checkout inherits workspace trust under `claude -p`; the documentation is silent and the opt-in e2e will record the answer.
- Whether `--permission-mode dontAsk` with explicit `Edit` and `Write` rules should replace `acceptEdits` in the default template.
- Monorepos: a per-package check command and scope-aware tool rules.
