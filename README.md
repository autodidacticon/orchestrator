# orchestrator

An orchestrator that runs many coding agents in parallel from a dependency graph of tasks against one repository. Dependencies gate admission. Each agent works in its own git worktree and reports through a local API. Humans resolve blockers and review milestones. A task is done only after its sealed work has been rebased, checked, and published to the integration branch. The orchestrator itself is a static TypeScript daemon with named hook points for model-backed judgment, designed to converge to the same outcome after a crash at any point. Task graphs are imported from Linear, Jira, or GitHub Issues through the session's own tracker connector (the `gh` CLI for GitHub), and progress is mirrored back to the tracker.

## Running locally

Prerequisites: Node 22.13 or newer (the store uses Node's built-in SQLite), git, and, for real agents, the Claude Code CLI (`claude`) logged in, or for Codex workers (`runner.kind: codex`, or tasks with `runner: codex`) the Codex CLI (`codex`) on PATH and logged in. Scripted agents need nothing else. Start from a Claude Code session with the plugin, or from a terminal with the CLIs.

### From a Claude Code session

Install the plugin from this repository's marketplace. Nothing else needs to be installed or on PATH:

```
claude plugin marketplace add autodidacticon/orchestrator
claude plugin install orchestrator@orchestrator
```

From a checkout instead, run `npm install && npm run build` once, then `claude --plugin-dir /path/to/orchestrator/hosts/claude-code`.

Then use the skills: `import` turns a Linear or Jira epic, or a GitHub issue or milestone with its sub-issues, into the graph with the session's own tracker connector, `run` starts the daemon, has the session's own subagents execute the launches through a bundled workflow, and monitors (questions, reviews, stuck tasks, proposals, tracker mirroring), `work` adds workers from another session or switches the mode, and `review` judges a milestone's pinned commit. On `start` the daemon detects the repository's check command, integration branch, and the tools agents may run, and the skill reports them with their sources; when nothing supplies a check command, the skill looks in `CLAUDE.md`, the README, and the root manifests and sets it through `configure`, or asks. No `orchestrator.yaml` is needed; the terminal section below describes the resolution order and the overrides. The plugin's launcher (`hosts/claude-code/bin/orchestrator.mjs`) runs the package from the plugin's own `node_modules` after a marketplace install (Claude Code installs the published package `@autodidacticon/orchestrator` pinned in `hosts/claude-code/package.json`), from the checkout when loaded with `--plugin-dir`, and through `npx` as a fallback.

Who executes launches is `runner.mode`: `pull` parks each prepared launch until a worker claims it, and is what a run started from the plugin defaults to, with the `run` skill's workflow claiming launches for visible session subagents; `spawn` has the daemon run headless Claude Code or Codex agents, and is the default for `orchestrator-ctl start` from a terminal, where no session is attached, and for a plugin-started run whose runner kind is `codex` (the `start` tool's `runnerKind` argument, or already in force for the run), because the plugin's pull-mode workers are the session's Claude subagents, which claim only `claude-code` launches; codex launches in `pull` are worked by the Codex work loop (`orchestrator-work`, [hosts/codex/README.md](hosts/codex/README.md) section 4), started from a shell, which claims with `runner: "codex"`, runs `codex exec` per claim with the spawned launch's command, and posts the usage back; `mixed` parks for `runner.claimWindowMs` (default 60 s) and then spawns. `runner.mode` in `orchestrator.yaml`, `orchestrator-ctl mode <mode>`, or `start` with `mode` are explicit choices that the plugin default never overrides. A claimed launch has no process: its lease is renewed by the worker's API calls and by progress in the worktree, and `release` hands it back (untouched: no attempt spent; with `--keep`, or `keep: true` on the tool, uncommitted work is committed on the launch branch, the branch is kept, and the task returns to unstarted at no cost with an `interrupted` context in its next brief, up to `daemon.maxKeptReleases` times, default 3).

### From a terminal

Build the package and put its executables on PATH:

```
git clone git@github.com:autodidacticon/orchestrator.git && cd orchestrator
npm install
npm run build
npm link            # puts orchestrator, orchestrator-ctl, orchestrator-mcp, orchestrator-mcp-shim, orchestrator-work on PATH
```

1. No configuration file is needed. At every start the daemon reads the repository root (never subdirectories) and detects the check command from the first matching manifest in a fixed order (a `Makefile` with a `test` target, then `package.json` with a real `test` script using the package manager named by `packageManager` or the lockfile, then `Cargo.toml`, `go.mod`, `pyproject.toml`/`setup.cfg`/`pytest.ini` with uv or poetry when their lockfile exists, `Gemfile`, `build.gradle(.kts)`, `pom.xml`, `mix.exs`, `*.sln`/`*.csproj`), the integration branch (`origin/HEAD` when that branch exists locally, else the checked-out branch, else `main`), and the tools spawned agents may run (`Bash(git:*)` and the orchestrator tools, plus the test, run, install, and exec commands of every toolchain found: `npm test`, `npm run`, `npm install`, `npm ci`, `npx`, `node`, `cargo`, `go`, `pytest`, `python`, `pip`, `uv`, `poetry`, `make`, and their counterparts). Every value is resolved in one order, an explicit argument over `orchestrator.yaml` over the branch pinned for the run (integration branch only) over detection over the built-in default, and records where it came from. Arguments are durable overrides for the run: `orchestrator-ctl start --set checkCommand="make check" --set capacity=3` (also `integrationBranch`, `allowedTools` as a JSON array or one rule per flag, `runnerCommand`, `runnerKind`, `model`, `effort`, and the per-kind keys `claude.model`, `claude.effort`, `claude.commit`, `codex.model`, `codex.effort`, `codex.sandbox`, `codex.commit`, `codex.command`, `codex.networkAccess`, and the limits `budgets.maxLaunchMs`, `health.stuckAfterMs`, `health.stuckFailAfterMs`), and `orchestrator-ctl config --check-command ... --capacity ... --allow "Bash(docker:*)" --runner-command ... --runner-kind codex --model ... --effort ... --sandbox ... --commit agent|daemon --clear <key>` on a running daemon (`--sandbox` sets `codex.sandbox`, `--commit` the commit policy of the kind in force, and `--clear` also takes a per-kind key such as `codex.sandbox`); `orchestrator-ctl config` alone prints every key with its value and source, the detection record, and `needsConfig`. The same facts are in `status` (`config`, `toolchain`, `needsConfig`) and in `config.json` in the run directory. When nothing supplies a check command, `needsConfig` names it and submitted work is held, without spending an attempt, until one is set. The integration branch is pinned when the run first starts: a re-pointed `origin/HEAD` or a different checked-out branch never moves it, and an explicit different branch is refused once the run holds launches (start from a fresh run directory to change it). The derived allow list lets spawned agents fetch and run packages, including their install scripts, with the user's credentials; `runner.claude.deriveTools: false` with an explicit `runner.claude.allowedTools`, or a `deny` rule in the project's `.claude/settings.json`, narrows it. Which agents get the list is the runner mode: it is filled into the `{allowedTools}` slot of the default `runnerCommand` for launches the daemon spawns (`spawn`, and `mixed` after the claim window), while a launch claimed by a session worker runs under that session's own permissions (see the previous section). Workers run `claude-opus-5-5` at `medium` effort by default (`runner.claude.model` and `runner.claude.effort`, overridable the same way); a task chooses its own with `model` and `effort` in its payload, which the import fills from `model:<name>` and `effort:<level>` labels on the issue. A task can also choose its runner kind with `runner: codex` (or `claude-code`) in its payload or a `runner:<kind>` label, so one run can mix Claude Code and Codex launches; a task without a `model` or `effort` then gets the chosen kind's defaults. The choice is fixed when a launch is prepared, filled into the `{model}` and `{effort}` slots of the default `runnerCommand` for spawned agents, carried in the claim response for session workers, and shown per launch in `status`. An existing `orchestrator.yaml` keeps working unchanged: keys it sets resolve with source `file`, and a `runnerCommand` without the `{allowedTools}`, `{model}`, or `{effort}` slots runs verbatim. The file is optional for everything else too:

   ```yaml
   integrationBranch: main
   checkCommand: npm test          # run on every rebased submission before it is published
   apiBind: 127.0.0.1              # the address the API binds; 0.0.0.0 in a cluster (file key, read at start)
   apiBaseUrl: http://orchestrator.orch.svc:8080   # the URL advertised to agents and clients when it differs from the bind
   capacity: 2                     # agents in parallel
   runner:
     kind: claude-code                    # or codex; a task's `runner` payload key or `runner:<kind>` label overrides it
     claude:
       allowedTools: ["Bash(docker:*)"]   # appended to the derived list for spawned agents
       deriveTools: true                  # false: only Bash(git:*), the orchestrator tools, and the rules above
       model: claude-opus-5-5             # worker model; a task's `model` payload key or `model:<name>` label overrides it
       effort: medium                     # low, medium, high, xhigh, or max; a task's `effort` key or `effort:<level>` label overrides it
     codex:
       model: gpt-6-astra                 # the Codex default model
       effort: medium                     # low, medium, high, xhigh, max, or ultra
       sandbox: workspace-write           # read-only, workspace-write, or danger-full-access
   scheduling:
     order: [criticalPath, priority, fifo]   # admission order; ties keep graph file order
     scopes: true                  # never run two tasks whose declared scopes overlap
   budgets:
     maxLaunchMs: 7200000          # 2 h per launch
     maxRunCostUsd: 20             # pause admission when the run has spent this much
     prices:                       # USD per million tokens, for runners that report tokens but no cost (Codex)
       gpt-6-astra: { inputPerMTok: 1.25, cachedInputPerMTok: 0.125, outputPerMTok: 10 }   # illustrative rates
   ```

   `runner.kind` picks the agent CLI: `claude-code` (the default) or `codex`, each with its own block, default model, and effort levels (Codex adds `ultra`). Select it in the file, or at runtime with `--set runnerKind=codex`, `orchestrator-ctl config --runner-kind codex`, the plugin's `start` or `configure` tool with `runnerKind: "codex"`, or `PUT /v1/config { runnerKind: "codex" }`; a flat `model` or `effort` argument binds to the kind in force, and `--set codex.model=...` (or `codex: { model, effort }` on the tools) names a kind's key directly. Under `codex` no allow list is composed (`config.allowedTools.applied` is false), and the daemon spawns `codex exec` for each launch. Codex reports token counts rather than a cost, so a Codex launch is priced from `budgets.prices` for its model; without a price its cost stays unknown and it is counted in `cost.unpricedLaunches`.

   ```yaml
   runner:
     kind: codex
     codex:
       model: gpt-6-astra        # the Codex default
       effort: medium            # low, medium, high, xhigh, max, or ultra
       sandbox: workspace-write  # read-only, workspace-write, or danger-full-access
       # commit: daemon          # unset: daemon, or agent under danger-full-access
   ```

   Each kind has a commit policy, `runner.<kind>.commit`: `agent` (the agent commits before it submits) or `daemon` (when the agent submits, the daemon commits what it left as `orchestrator` with the report summary as the message, and `agent.report` records `committedByOrchestrator: true`). `runner.claude.commit` defaults to `agent`. `runner.codex.sandbox` defaults to `workspace-write`, and `runner.codex.commit`, when unset, is derived from the sandbox: `daemon`, or `agent` under `danger-full-access`. The reason is a known limitation of Codex's `workspace-write` sandbox: it cannot `git commit` in a linked worktree. The index lock under `<repo>/.git/worktrees/<wt>/` is refused, and `--add-dir` or `writable_roots` do not help, because Codex keeps the gitdir read-only. A clean worktree is never committed, so a no-op still needs `noChanges`. All three keys can be changed at runtime (`--set codex.sandbox=...`, `--set codex.commit=...`, `--set claude.commit=daemon`) and apply to launches prepared afterwards. `danger-full-access` gives Codex the same unsandboxed access the Claude runner has; whether `git commit` works under it has not been probed. `runner.codex.networkAccess` (unset by default) is the override leaf `codex.networkAccess`: `true` or `false` through `--set codex.networkAccess=...`, `orchestrator-ctl config --set` and `--clear codex.networkAccess`, the `start` and `configure` tools' `networkAccess` argument, or `PUT /v1/config { codex: { networkAccess } }`, where `null` clears it; a stored `false` wins over a file's `true`. It is read when a launch's command is composed, so a running launch keeps its command line. When true, the runner passes `-c sandbox_workspace_write.network_access=true` whatever the sandbox; whether that gives a sandboxed command registry access or lets a test open a port has not been shown by a real Codex run. Set it only when the user asks for it: it widens what a Codex worker can reach. The brief of a `codex` launch states whether the worker's commands have network access: yes under `danger-full-access`, yes under `workspace-write` with `runner.codex.networkAccess` true, no otherwise (`brief.json` `runner.networkAccess`). Without it, the Definition of done tells the worker to run the parts of the check that do run and, when the rest cannot run for lack of network or because an install writes to a package store outside the worktree, to submit and name each part that did not run and its error in the report summary, not to ask with `needsAccess`; the orchestrator runs the check itself outside the sandbox after the submit. A login, a credential or a token is still asked for with `needsAccess`. The cost: such a worker can submit untested work, and a failed check spends an attempt (`maxAttempts` defaults to 2).

2. Start the daemon for that repository. It records run data under `~/.orchestrator/runs/<id>/` and prints the graph file path:

   ```
   cd /path/to/your/repo
   orchestrator-ctl start          # {"started": true, "url": "http://127.0.0.1:...", "graphPath": "~/.orchestrator/runs/<id>/graph.yaml", ...}
   ```

3. Write the task graph to that `graphPath`. The daemon re-reads it on change. Every task needs a description and acceptance criteria, or it is blocked as under-specified:

   ```yaml
   nodes:
     - id: T1
       title: Add the schema migration
       description: Create the users table migration and the model.
       acceptanceCriteria: [migration applies cleanly, model has unit tests]
       deps: []
     - id: T2
       title: Expose the users API
       description: Add GET and POST /users on top of T1's model.
       acceptanceCriteria: [endpoints documented, integration test passes]
       deps: [T1]
       scope: ["src/api/**", "package.json"]   # optional: path globs the work stays within
       priority: 1                             # optional: lower is more urgent
     - id: MVP
       kind: milestone
       gated: true                 # a human reviews and accepts the pinned commit
       deps: [T2]
   ```

4. Operate the run from the same terminal:

   ```
   orchestrator-ctl status                         # sets by state, stall roots, open questions, stuck tasks, deferred tasks, cost, config, toolchain, needsConfig
   orchestrator-ctl config [--check-command <cmd>] [--allow <rule>] [--capacity <n>] [--runner-kind <kind>] [--sandbox <mode>] [--commit <policy>] [--set key=value] [--clear <key>] [--end-live]   # show or override the configuration
   orchestrator-ctl answer T1 "use sqlite"         # answer an agent's question
   orchestrator-ctl cancel <task> [--release] [--reason <text>]
   orchestrator-ctl unblock <task> [--answer <text>] [--accept-candidate]
   orchestrator-ctl review <milestone> [--task <id>] [--full] [--stat-lines <n>] [--summary-chars <n>]   # the review index; one task, or the whole bundle
   orchestrator-ctl logs T1                        # the agent's captured output
   orchestrator-ctl nudge T1 "commit what you have"
   orchestrator-ctl accept MVP --sha <sha> --version 1   # or: reject MVP --note "..."
   orchestrator-ctl reopen T1 [--cascade]
   orchestrator-ctl proposals | accept-proposal <id> | reject-proposal <id> --note "..."
   orchestrator-ctl pause | resume [--override-budget]
   orchestrator-ctl mode pull | claim w1 | release <launchId> --reason "..."
   orchestrator-ctl stop [--reap]                  # graceful: agents keep running and are adopted on the next start
   orchestrator-ctl runs                           # every run under ~/.orchestrator
   ```

   The daemon exits on its own after `daemon.idleExitMs` (default 10 min, 0 disables) with nothing live and no session attached (`daemon.exitWhileAttached: true` lets it exit while one is), records why in `daemon.json` (`runs` shows `exit` for a daemon that is gone, or nothing after a crash), and any `orchestrator-ctl` command or plugin tool revives it on demand; only an explicit `stop` is final until the next `start`. `status` reports `idle` and `attachments`. To run the daemon in the foreground instead, `orchestrator --repo .` (SIGTERM stops it gracefully). To keep everything inside one directory, use a config with explicit paths and `orchestrator --config orchestrator.yaml` with `repoPath`, `graphPath`, and `dataDir` set; then pass `--data-dir` to `orchestrator-ctl`.

By default agents are headless Claude Code sessions (`runnerCommand`, with `{allowedTools}`, `{model}`, and `{effort}` filled at spawn), or headless Codex sessions (`codex exec`) under `runner.kind: codex`, each in its own git worktree with the brief on stdin and the agent API as an MCP server. For a dry run without model calls, point `runnerCommand` at the scripted agent: `node --import <repo>/node_modules/tsx/dist/loader.mjs <repo>/test/agents/scripted.ts {briefJson}`, and give each task a `behavior` such as `commitAndSubmit`, `blockAndWait:<question>`, or `fail`.

### Tests

`npm test` runs everything that needs no model: unit tests, slices with real subprocess agents, git, and the HTTP API, and the crash-injection suite in `test/crash`, which is the project gate. Eight opt-in tests use a real model: `ORCH_E2E_CLAUDE=1 npm test -- test/e2e/claude` runs three Claude Code agents, `ORCH_E2E_CLAUDE_PLUGIN=1 npm test -- test/e2e/plugin` has a Claude Code session operate a run through the plugin, and `ORCH_E2E_CLAUDE_WORK=1 npm test -- test/e2e/work` has a session execute a run in pull mode with two workers through the work skill. `ORCH_E2E_CODEX_OPERATOR=1 npm test -- test/e2e/codex-operator` has `codex exec` operate a spawn-mode run of scripted agents through the operator server to `finished`. `ORCH_E2E_CODEX=1 npm test -- test/e2e/codex` has Codex workers (a logged-in `codex` on PATH; skipped with a warning without one) publish three tasks plus a fourth whose `block` is answered after 90 s, and checks recorded tokens, the daemon commit policy, and the MCP tool timeout. `ORCH_E2E_CODEX_WORK=1 npm test -- test/e2e/codex-work` has two Codex work loops drain a three-task pull-mode graph. `ORCH_E2E_CODEX_NETWORK=1 npm test -- test/e2e/codex-network` probes what a Codex worker under `workspace-write` can reach with `runner.codex.networkAccess` on (a logged-in `codex` and access to registry.npmjs.org; it costs tokens). `ORCH_E2E_OPENCODE=1 npm test -- test/e2e/opencode` has OpenCode workers on the free model `opencode/big-pickle` (no login or key needed; skipped with a warning naming `opencode` when it is not on PATH) publish three tasks at capacity 2, one of whose `block` is answered after 75 s, and checks recorded tokens with cost 0 from the stream, the agent commit policy, and that `startupContended` relaunches are not charged. A second case, a `needsAccess` question for a command outside the derived permission patterns, is skipped: opencode 1.18.30 ends a run on an auto-rejected `ask`. `ORCH_E2E_OPENCODE_RECORD=1` also copies the launches' JSONL, redacted, to `test/fixtures/opencode/e2e-*.jsonl`. One more opt-in check uses no model: `ORCH_E2E_CODEX_HOST=1 npm test -- test/host/codex-host` runs `codex mcp get` against the host's config template, lets the installed `codex` render the template's SessionEnd hook, and installs the Codex plugin from this checkout into a scratch `CODEX_HOME` and has `codex exec` call its `start` tool with `repo` (that last step uses a model; all skipped with a warning without a `codex` on PATH).

### Running on Kubernetes

The daemon also runs as a long-lived container. This path needs a clone of this repository at the tag of the installed version: the npm package ships neither `deploy/` nor the `Dockerfile`, and the image is built locally. `deploy/README.md` in that clone is the operational reference: the `Dockerfile` builds an image with Node, git, and ssh only (`orchestrator` and `orchestrator-ctl` on PATH); `deploy/base` is a kustomize layout with a Recreate Deployment that clones `REPO_URL` into an `emptyDir` with no volume claim, so every pod starts from a fresh clone, keeps the run's state in a CloudNativePG cluster (the CloudNativePG operator must be installed first), probes `/healthz` and `/readyz`, and runs in pull mode behind a ClusterIP Service; `deploy/overlays/kind` adds an in-cluster git origin and a two-task graph; and `deploy/smoke.sh` builds, loads into kind, applies the overlay, and asserts the milestone claims over the API (`--dry-run` prints the steps). The cluster-facing settings are `apiBind` and `apiBaseUrl` (the address the API binds and the URL it advertises; file keys read at start, not runtime overrides), `ORCH_LOG_FORMAT=json` for one JSON object per log line, and `ORCH_URL` on a client naming a non-loopback host, which makes `orchestrator-ctl` and the operator MCP server use that daemon without ever starting a local one. Workers do not yet run in the cluster: a daemon there parks launches for session workers. The graph lives in the store and is sent with `PUT /v1/graph`, so import and proposal acceptance work in that layout. `deploy/base` and the kind overlay are a preview for one user on a kind cluster, not a layout for a shared cluster: the API takes no credential except the launch token, which only a worker's own routes read, so any caller that reaches the Service can operate the run and set the commands it runs. Do not expose the Service through an Ingress, a NodePort or a LoadBalancer. Authentication comes with the hardening milestone. The specification is [cluster-runtime](openspec/specs/cluster-runtime/spec.md) and the "Container mode" requirement of [operator-control](openspec/specs/operator-control/spec.md).

## Upgrading from 0.5.1

What changes for a 0.5.1 user who installs 0.6.0. The behaviour itself is described under Behaviour.

- **Database variables in child environments.** 0.5.1 removed only `ORCH_URL`, `ORCH_REPO` and `ORCH_DATA_DIR` from the environment of agents and check commands: it passed `DATABASE_URL`, `DATABASE_URL_FILE` and the `PG*` variables to checks and agents unchanged, as 0.5.0 did. 0.6.0 removes `ORCH_RUN_ID` from children on every store kind. Under `store.kind: sqlite` (the default) the database variables pass as in 0.5.1, except when the config file does not write `store.kind` while it sets another `store` key or the environment sets `ORCH_RUN_ID`: then the daemon removes them and logs the `postgresInputsUnderSqlite` warning. Under `store.kind: postgres` 0.6.0 removes them (`DATABASE_URL`, `DATABASE_URL_FILE`, libpq's variables, and any variable under another name whose value is the store URL) from check commands, from spawned agents of every runner kind, and from the daemon's git commands and their hooks; agents that `orchestrator-work` runs for a claim lose those names too, through the claim's environment block. A Postgres run whose project tests need a database should put the project's connection settings in a file the project's test runner loads, not in `checkCommand`: the `config.resolved` event records the check command with its value.
- **New config keys.** File keys read at start, not runtime overrides: `health.gapAfterMs` (default 60000: two clock readings further apart are a gap; 0 off), `health.gapHoldMs` (default 60000: how long nothing starts after a gap; 0 off), `review.statLines` (default 40) and `review.summaryChars` (default 400), the review index's cuts, `store.schema` (default `orchestrator`, Postgres only: the schema of the store's tables), `prepareCommand` (unset: run in every prepared worktree), `prepareTimeoutMs` (default 600000), `prepareFailureLimit` (default 3) and `prepareRetryBackoffMs` (default 30000), and `runner.confirmProfile` (default `false`: the profile hold, written into the run's stored choice at every start). Changeable on a running daemon: `budgets.maxLaunchMs` (default 7200000), `health.stuckAfterMs` (default 900000) and `health.stuckFailAfterMs` (default 2700000), which 0.5.1 read only from the file, and the new leaf `codex.networkAccess` (`runner.codex.networkAccess`, unset by default).
- **Review answer.** The `review` tool and `GET /v1/milestones/<id>/review` answer an index by default (`view: "index"`), with the diff stat and the summaries cut, not the whole bundle. `task=<id>` returns one task; `full=true` returns the whole bundle as 0.5.1 did, with `view` and `omitted` first (and `previous` above version 1). The same choices are `orchestrator-ctl review <milestone> [--task <id>] [--full]`, a new command. The ready-for-review tracker comment is a short notice, and `wait` returns a submitted event cut like the index.
- **`ack` and `nack`.** The answer's `effect` no longer carries the effect's `payload`: it has `id`, `taskId`, `kind`, `status` and `attempts`, plus `result` and `error` when present. A script that read `effect.payload` from the answer reads it from the `outbox` listing (`GET /v1/outbox`, `orchestrator-ctl outbox`), which still returns payloads.
- **Requests with an `Origin` header.** The API answers 403 with `code: originHeader` to any request that carries an `Origin` header, on every bind, and on a loopback bind 403 with `code: hostHeader` to a request whose `Host` is not the bound address, `localhost` or the host of `apiBaseUrl`, each with the port. A browser page, or a tool that sets the header, is refused. A user who reaches a loopback daemon through a tunnel or an `/etc/hosts` alias sets `apiBaseUrl` to that URL. `orchestrator-ctl`, the MCP servers and a plain `curl` send no `Origin` header and use the bound address, so they are not affected.
- **Profile hold.** A run that existed before the update has no stored choice. It adopts the profile hold the next time a host tool spawns its daemon (`start`, or any tool after an idle exit or a crash), and its `unstarted` tasks, retries included, are then held until a model and an effort are set. A daemon that is already running keeps what it has, and a remote daemon gets the hold only from its own file.
- **Codex workers.** Codex workers under `workspace-write` (the default sandbox) now submit instead of asking the operator when the check command cannot run in the sandbox for lack of network: expect fewer `needsAccess` questions, and read the report summary for the parts of the check the worker did not run.
- **Going back to 0.5.1.** A 0.5.1 daemon reads the stored override document through a strict schema and reads the whole document as empty when it holds a key it does not know. A stored override of `budgets.maxLaunchMs`, `health.stuckAfterMs`, `health.stuckFailAfterMs` or `codex.networkAccess` therefore makes a 0.5.1 daemon drop every override, not just those keys: `checkCommand`, `runnerKind`, `allowedTools`, `capacity`, the model, effort, sandbox and commit overrides are all lost until set again, and nothing is logged. Before going back, clear the new keys (`orchestrator-ctl config --clear budgets --clear health --clear codex.networkAccess`), or set the overrides again afterwards. Nobody has tested that a 0.5.1 daemon opens a run directory a 0.6.0 daemon wrote, so this is not a promise that a downgrade works.
- **Versions to install.** The package `@autodidacticon/orchestrator@0.6.0`. Claude Code: the plugin `orchestrator@orchestrator` at 0.6.0, installed as in "From a Claude Code session" (this README documents no update command for it). Codex: the plugin `orchestrator-codex@orchestrator` at 0.6.0: run `codex plugin marketplace upgrade orchestrator`, then `codex plugin add orchestrator-codex@orchestrator`. OpenCode: the launcher resolves the package from a checkout, then from `hosts/opencode/node_modules`, then from `npx` at the pinned version ([hosts/opencode/README.md](hosts/opencode/README.md) section 1), so bring that checkout to 0.6.0, and run `npm install` in `hosts/opencode` again if that copy is the one used. A checkout: bring it to the tag `v0.6.0`, then run `npm install && npm run build`; `npm install` is needed because `pg` is a new dependency that the daemon imports at start under every store kind, SQLite included. A running daemon must be stopped and started (`orchestrator-ctl stop`, then `orchestrator-ctl start`) to run the new code: a 0.5.1 daemon still running after the update answers 400 to the new keys. Update every host and the package together.

## Behaviour

A task is done once its sealed work has been rebased onto the integration branch, checked, and published as one squash commit with `Orchestrator-Task` and `Orchestrator-Launch` trailers; a gated milestone then waits for a human to accept its pinned commit. The daemon converges to the same outcome after a crash at any named point, and surviving agents are adopted on restart.

Child processes. Spawned agents of every runner kind, check commands, and the daemon's own git commands with the hooks they run inherit the daemon's environment with `ORCH_HOME` pointed inside the run's data directory and the client-side variables (`ORCH_URL`, `ORCH_REPO`, `ORCH_DATA_DIR`) and `ORCH_RUN_ID` removed, so repository code they run cannot discover or stop the user's daemons; `ORCH_API` stays, since the agent shim needs its own daemon. The database variables follow the store the daemon opened: on a Postgres store, `DATABASE_URL`, `DATABASE_URL_FILE`, libpq's connection variables (`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGSERVICE`, `PGPASSFILE`, the `PGSSL*` names and the rest of libpq's list) and any variable whose value is the store URL are removed too; on a SQLite store they pass. The exception: a SQLite daemon whose config file does not write `store.kind` while it sets another `store` key or the environment sets `ORCH_RUN_ID` keeps removing them and logs a warning (event `config.warning`, code `postgresInputsUnderSqlite`); write `store.kind: sqlite` to pass them. The config report's store block says which rule is in force (`withholdsDatabaseVariables`). A `shutdown` through the route records who asked (attachment id, remote address, user agent) in an `operator.shutdown` event and in the exit record, and the revival refusal after a stop names the caller.

Store and origin. Both are off by default. `store.kind` is `sqlite` (the file `store.sqlite` in the run directory) unless it is set to `postgres`, which keeps the run's state as a journaled memory image flushed to the database named by `store.url`, `store.urlFile`, `DATABASE_URL_FILE` or `DATABASE_URL`. `git.pushIntegration` (default `false`) makes origin the source of truth: the verifier fetches before each job and pushes each publication with a lease, base selection reads origin's head, and milestone tags are pushed; off, no git command contacts a remote. A switch of `store.kind` starts an empty run: the daemon opens the other store, and the SQLite file is left as it was. Under Postgres the graph lives in the store: it is sent with `PUT /v1/graph`, proposal acceptance reads it there, and step 3's graph file is not read. The tables live in the schema `orchestrator`, or the one `store.schema` names (a config-file key read at start), which is created when absent; tables in any other schema, `public` included, are not read, and an empty run logs one warning (event `config.warning`, code `tablesInOtherSchema`) when another schema of the database holds orchestrator tables. A daemon refuses to open a database whose `orchestrator_migrations` records a version it does not know; it checks this at startup only. Under SQLite `DATABASE_URL` is not a store input, so it never shows up as `store.url`. The keys, the run id per deployment and the store credentials are described in `deploy/README.md`, in a clone at the tag of the installed version. In `mixed` mode a launch parked for the claim window is either claimed by a worker or spawned by the daemon, never both: the spawn pass reads the row again and moves it out of `claimable` in one step, and a claim takes only a `claimable` launch; the Codex work loop (`orchestrator-work`) renews the lease of a launch it claimed while its agent runs.

Worker profile hold. `runner.confirmProfile` (default `false`) holds, at admission, every `unstarted` task whose model or effort would come from a built-in default, for every runner kind, `claude-code` included; a retry is held like a first launch, and live, parked and waiting launches are not touched. A value from `start`, `configure`, `--set`, or `runner.<kind>.model` / `runner.<kind>.effort` in `orchestrator.yaml` confirms that key, also when it equals the built-in value; a value in a task's own payload or labels is never held. In `spawn` mode a key the runner command has no slot for (`applied: false`) is not a reason to hold; in `pull` and `mixed` mode it is. The hold is not a pause: `paused` stays false. `status.profiles` groups what every task that has not started will run with (`runner`, `model`, `effort`), the source of each value (`task`, `argument`, `file`, `default`), `held`, `missing`, a count and up to 5 ids; `status.runner.confirmProfile` is the hold in force, and the wait digest has `profileHeld`. A run started through a host's `start` tool (the Claude Code, Codex or OpenCode plugin) holds: the tool starts the daemon with `--default-confirm-profile on`, which is adopted only when the file does not state `runner.confirmProfile` and the run has no stored choice, and the `start` result carries `confirmProfile`. The choice is stored in the run, so after one start by a host tool `orchestrator-ctl start` on the same run holds too; `orchestrator-ctl start`, a daemon started by hand and a cluster daemon never turn the hold on by themselves. `runner.confirmProfile` in `orchestrator.yaml` overwrites the stored choice at every daemon start (unlike `runner.mode`), so `false` there and a restart turn the hold off; there is no runtime switch. To avoid being asked per run, set `runner.<kind>.model` and `runner.<kind>.effort` in `orchestrator.yaml`. The `start` and `configure` tools take a `claude` object (`model`, `effort`) beside `codex` and `opencode`, so the Claude Code leaves can be set while another kind is in force.

Prepare command. `prepareCommand` (unset by default) and `prepareTimeoutMs` (default 600000) are config-file keys read at start, not overrides: `start`, `configure` and `--set` do not take them, and changing the command needs a daemon restart. With the command set, the daemon runs it in every worktree it prepares, for every runner kind and mode, outside any agent sandbox and with the check command's environment, in the background while it keeps ticking; the launch is spawned or becomes claimable only after the command exited 0. A command that exited but left a process holding its output is killed at `prepareTimeoutMs` and recorded as a timeout. A pause, and the hold after a clock gap, do not interrupt a running command, but no new command starts and no prepared launch is spawned during them; in `spawn` mode a launch whose command finished while paused waits for the resume, and the daemon does not exit for idleness while it waits. Its task is running meanwhile, so it holds a capacity slot and its scope. Afterwards the worktree must be clean apart from `.orchestrator/`, so the install tree must be ignored by the repository's git. A failure (non-zero exit, timeout, killed, cannot start, dirty worktree) spends no attempt: the launch ends with `prepareCommandFailed`, and the task is launched again after `prepareRetryBackoffMs` (default 30000) doubled per earlier failure, the factor capped at 32, and is blocked with kind `prepareFailed` after `prepareFailureLimit` (default 3) failures in a row; both are file keys read at start. A failure that overlapped a machine sleep counts like any other, and the backoff counts wall time. While a task waits for its retry it holds no capacity slot, and the daemon does not exit for idleness. A cancel, a cascade reset, a stop or a crash during a command counts nothing: a stop kills the command, and the next start runs it again for the same attempt. The count is cleared by a successful run, at the block, and on unblock, reopen, uncancel and cascade; the blocked message names the command, the count and the last reason, never the output. Events: `launch.prepareStarted`, `launch.prepared`, `launch.prepareFailed` (with the last 4096 characters of the output, which reach an operator through `wait` and `/v1/events`). `status` has `preparing`, `prepareRetry` and `preparingByKind`, the wait digest `preparing` and `preparingByKind`; a task waiting for a prepare retry is listed in `prepareRetry` and counted in `preparingByKind` while it is `unstarted`, also after its `retryAt` has passed, until it is launched, blocked or cancelled, and a task is counted once; in `mixed` mode a launch the daemon took back and prepares again (`launching`) counts in `preparingByKind` too. `orchestrator-work` and the Claude Code work workflow do not stop while `preparingByKind` for their kind is above 0. The brief says the orchestrator ran the command in the worktree outside any sandbox and that the worker should not run it again unless its change needs it. The verifier runs the command in its temporary worktree right before the check command; there a failure spends an attempt like a failing check (`checkFailed`, or `checkTimeout` for a timeout), and the job's output starts with `prepare command exited <code>` or `prepare command exceeded <ms>ms`. A declared no-op runs neither command there, and every other job pays one install. In `mixed` mode a parked launch that the daemon spawns after the claim window is prepared a second time, so the command runs twice for it. A mode change from `pull` to `spawn` during an install also runs it twice, and a crash during a second run can give a third; a launch admitted in `spawn` mode is spawned by the daemon even if the mode changes to `pull` during its install. After a restart, a parked launch whose worktree is lost, that was parked before the key was set, or that was parked under another command text is ended at no cost (`notPrepared`) and made again; the task's next brief shows a prior failure whose message says nothing was wrong with the task. A wrong command, or a long registry outage, blocks every admitted task one by one, each with its own `prepareFailed` block. To recover from a wrong command: stop the daemon, fix `prepareCommand` in `orchestrator.yaml`, start, and unblock each blocked task.

Tracker sync. After an import that names its tracker, the daemon derives tracker-bound effects from its own transitions into a durable outbox, in the same transaction as the transition: an issue goes in progress on its first launch, done when its work is published (or, with `tracker.doneAt: milestoneAccepted`, when its gated milestone is accepted), cancelled on cancel; the parent issue follows its first starting child and closes when the milestone is accepted. Comments are posted where a human is needed: an agent's question, a block with its reason, a milestone ready for review, accepted, or rejected (`tracker.commentOnDone` and `tracker.commentOnFail` add completion and failure comments, both off by default). The daemon never talks to a tracker: the `run` skill drains the outbox after every `wait` with the session's Linear or Atlassian tools, mapping states by type, and acknowledges each effect (`outbox`, `ack` tools; `GET /v1/outbox`, `POST /v1/outbox/:id/{ack,nack}` routes; `orchestrator-ctl outbox | ack`). An `ack` or `nack` answers the effect's `id`, `taskId`, `kind`, `status` and `attempts`, plus `result` and `error` when present, and not its payload, which the drainer has from the `outbox` listing. The ready-for-review comment is a short notice: the milestone, its version, sha and tag, and a pointer to the `review` tool and `orchestrator-ctl review <id>`. Every comment ends with a marker line, `— orchestrator run <id> · event <n>`, so a drainer can recognise its own comments and never posts one twice. A human reply under a question comment is relayed as the answer (`tracker.answersFromComments`, default on); the first answer wins. Config keys: `tracker.enabled` (`auto` | `always` | `never`), `maxAttempts`, `parentInProgress`, `doneAt`, `commentOnDone`, `commentOnFail`, `answersFromComments`. Status reports `tracker`, `outboxPending`, and `trackerErrors`. Manual check against a sandbox workspace: import an epic with the `import` skill in a Claude Code session connected to Linear or Jira, run it with the `run` skill, and watch the child issues move and the question comment appear; this is not part of `npm test`.

The daemon's life. A session attaches through the plugin's operator server, which registers its process ancestry with the daemon on first contact and ends the attachment when its transport closes; the plugin's `SessionEnd` hook posts the ending session's ancestry as well, and the daemon ends any attachment whose own process has died. A claim made through a session carries its attachment, and when the attachment ends the daemon releases that launch with `keep` on the next tick: uncommitted work becomes a work-in-progress commit on the launch branch, the worktree goes, the branch stays, the task returns to `unstarted` with `attempts` unchanged and an `interrupted` context (prior launch, branch, head, the WIP commit) in its next brief, counted in `interruptions` and bounded by `daemon.maxKeptReleases`. With nothing live, no verifier job pending, no cascade pending, no request in flight, and no session attached, the daemon exits after `daemon.idleExitMs`, writes an exit record, and is revived by the next operator call; the plugin's `SessionStart` hook names runs whose daemon is alive or whose last exit left parked launches, open questions, a milestone under review, or a stall. Releasing a new version: bump the version in ten places: `package.json`, `package-lock.json` (twice: the top-level `version` and the root package's entry), `hosts/claude-code/.claude-plugin/plugin.json`, `hosts/codex/.codex-plugin/plugin.json`, the pins in `hosts/claude-code/package.json`, `hosts/codex/package.json` and `hosts/opencode/package.json`, and the MCP server versions in `src/agent/mcp-shim.ts` and `src/operator/mcp-server.ts`; commit, and tag the commit `v<version>` with an annotated tag; `npm publish` (which builds); regenerate `hosts/claude-code/package-lock.json` with `npm install --package-lock-only` in that directory against the published version; then push the branch and the tag.

Scheduling. Ready tasks are admitted in the order of `scheduling.order`, a chain of stages applied as one stable sort (default `[criticalPath, priority, fifo]`): `criticalPath` puts the task with the longest chain of tasks behind it first, so the chain that gates the milestone starts first; `priority` reads the task's `priority` as a number, lower first, missing last (the import passes the tracker's number through, dropping Linear's 0); `fifo` is graph file order, which also breaks any remaining tie. Waiting tasks whose answer has arrived are resumed before anything is ordered; `order: [fifo]` restores the v1 order. A task may declare `scope`, a list of path globs (in the graph file, or under a `Scope` heading in an imported description, one glob per bullet; `options.scopeHeading` renames it). While a task is running, waiting, submitted, or has a claimable launch, no task whose scope overlaps it is launched: two globs overlap when the static prefix of one (the leading path segments before any `*`, `?`, `[`, `{`) is a prefix of the other's, so `src/**` holds `src/api/x.ts`, `src/api/**` and `src/ui/**` run together, and `**` or `*` overlaps everything. Held-back tasks appear as `deferred: [{ id, reason: scopeOverlap, with }]` in status and as a count in the digest; they launch on the first tick after the blocker publishes. `scheduling.scopes: false` turns the filter off; a malformed `scope` fails graph validation.

Health. The daemon renews a launch's lease every tick while its process is alive; lease expiry applies only to launches the runner cannot observe. Progress is a worktree fingerprint (head plus status and diff), any API call, or a changed heartbeat text. A launch idle past `health.stuckAfterMs` (default 15 min) is flagged (`stuck` in status and the digest, a `stuck` notice in its inbox, event `launch.stuck`) and idle past `health.stuckFailAfterMs` (default 45 min) is reaped and failed with reason `stuck`, spending an attempt; either threshold at 0 disables that step. `orchestrator-ctl nudge <task> <message>` (also the `nudge` tool) queues a message for the agent's inbox. Budgets: `budgets.maxLaunchMs` (default 2 h) fails an overlong launch with reason `timeBudget`, waiting time excluded (a spawned launch counts from its spawn, a claimed one from when it was parked); `budgets.maxRunCostUsd` (default 0, unlimited) pauses admission with `pausedReason: costBudget` once the run's cost, read per launch from Claude Code's final JSON or computed from Codex's token counts times the `budgets.prices` entry for the launch's model, reaches the ceiling (an unpriced Codex launch has no cost and is counted in `cost.unpricedLaunches`), and `resume` is refused until `orchestrator-ctl resume --override-budget` (or `resume` with `overrideBudget`) raises the ceiling by one budget. When a task is published, every other running agent gets a `baseMoved` notice naming the new head and the files it touched, and may rebase its branch onto it; the verifier rebases from the merge base so such branches integrate cleanly (`health.baseMovedNotice` turns the notice off). A machine that sleeps does not end launches at the wake: the daemon reads its clock about once a second, and two readings more than `health.gapAfterMs` apart (default 1 min) are a gap, written as a `daemon.gap` event (`from`, `to`, `gapMs`, `holdUntil`). A gap does not count towards `health.stuckAfterMs`, `health.stuckFailAfterMs` or `budgets.maxLaunchMs`, writing it renews every live launch's lease for a full TTL without counting as progress, and `idleMs` and `elapsedMs` in status now leave gaps out. For `health.gapHoldMs` after a gap (default 1 min) nothing is admitted, resumed, spawned or verified, so the agents still running can check in first; claims are still served, and the daemon does not exit for idleness during the hold. A check that fails (`checkFailed` or `checkTimeout`, or a verifier run that throws) across a gap is run again once without spending an attempt: the job goes back to `queued` with `gapRequeues: 1` and a `verify.requeued` event whose `gap` gives the failure kind and `gapMs`, and a second failure of the same job is charged as usual (`checkTimeoutMs` itself still counts wall time). Either key at 0 turns its part off. Not covered: `maxWaitMs` still counts the sleep; an agent that ends itself at the wake is a failed attempt as before; a daemon that was stopped and started again counts the time in between as running time, and one restarted during a hold admits at once; under `store.kind: postgres` a sleep longer than `store.flushDeadlineMs` with a write pending still ends the daemon; a stopped or frozen daemon process is a gap too, so the limits lengthen by the stall; a very small positive `health.gapAfterMs` turns ordinary pauses of the daemon into gaps; and the `daemon.gap` event is the only trace of a hold (status has no field for it). The Codex work loop applies the same rule to its own silence timer: `orchestrator-work` leaves its own machine's sleep out of the silence it measures (`--gap-after-ms`, default 60000, 0 off). The three limits `budgets.maxLaunchMs`, `health.stuckAfterMs` and `health.stuckFailAfterMs` can be changed on a running daemon, in milliseconds with 0 disabling the limit, under those dotted names: `orchestrator-ctl config --set budgets.maxLaunchMs=...` and `--clear`, `orchestrator-ctl start --set`, the `configure` and `start` tools (`budgets` and `health` objects), and `PUT /v1/config` with nested blocks (`{ budgets: { maxLaunchMs }, health: { stuckAfterMs, stuckFailAfterMs } }`); with both stuck limits above 0, `health.stuckFailAfterMs` must be above `health.stuckAfterMs`. The config report shows each with its value and source. A change that would end a live launch now (a lowered, cleared or switched-on limit it is already past) is answered 409 with `wouldEnd` and nothing is applied; `endLive: true` in the body, `endLive` on the `configure` tool, or `orchestrator-ctl config --end-live` confirms it. The guard covers the route only, not a daemon started with `--set` or a changed file. Each affected worker gets a `nudge` notice with `source: 'config'` naming the old and new values; a worker that does not read its inbox does not learn of it, and a work loop without `--max-silence-ms` follows `health.stuckFailAfterMs` from `status`. Every brief states the stuck limits and the time budget in force when it was written, in a `Limits:` line.

Graph mutation. Milestones hold no work, so they never block a reopen: reopening a done task resets every done or submitted milestone downstream (`milestone.reset`), which is reviewed again at its next version once the revised work is published, and dependency edits to such milestones are compatible reloads that reset them the same way. A reopen whose target has started task dependents is refused with the blockers; `orchestrator-ctl reopen <task> --cascade` (or `reopen` with `cascade: true`) records a plan, returns it as `reset: [{ id, from }]`, and the next tick kills running dependents, drops queued verification, and returns done dependents and the target to unstarted with budgets reset. Nothing on the integration branch is reverted: each relaunch is briefed with a revision context naming the prior launch, branch, published commit, and report, and publishes a further trailer commit. Agents may put structured `proposals` (title, description, acceptance criteria, optional deps, scope, labels) in their submit report; they are held pending (`proposals` in status and the digest) until `accept-proposal <id> [--node-id <tracker key>]` appends a task node depending on the proposer, joining its gated milestone when `proposals.joinMilestone` is true (default), or `reject-proposal <id> --note`. A compatible reload that edits a running task's payload sends its agent a `payloadChanged` inbox notice (`graph.payloadChangedNotice`, default true); the pinned brief stays and the next launch uses the new payload.

Review. The review answer (the `review` tool, `GET /v1/milestones/<id>/review`, `orchestrator-ctl review <milestone>`) is an index by default (`view: "index"`): the diff stat cut to `review.statLines` file lines (default 40) with git's totals line kept, each task's summary cut to `review.summaryChars` UTF-16 units (default 400), and an `omitted` list that gives each cut's count and how to fetch what it left out. `task=<id>` (`--task <id>`) answers one closure task with its own criteria, its changed files and its whole latest report; `full=true` (`--full`) answers the whole bundle as before, with `view: "full"`. `review.statLines` and `review.summaryChars` are file keys read at start; the request parameters `statLines` and `summaryChars` (`--stat-lines`, `--summary-chars`) override them for one call. Above review version 1 the index and the full answer carry `previous`: the earlier version, its sha and tag, and the tasks added or republished since (`tasksSinceUnavailable: true` in place of that list when the earlier submitted event is missing, names another commit, or holds no readable closure); when no sha is on record for the earlier version, `previous` holds only the version and `unavailable`, and the review skills then review the whole closure as for a first version. The `wait` tool returns a milestone's submitted event cut like the index (`GET /v1/events?cutSubmitted=true`), and `review` holds the rest. `accept` still needs `--sha` and `--version`.
