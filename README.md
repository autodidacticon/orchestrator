# orchestrator

An orchestrator that runs many coding agents in parallel from a dependency graph of tasks against one repository. Dependencies gate admission. Each agent works in its own git worktree and reports through a local API. Humans resolve blockers and review milestones. A task is done only after its sealed work has been rebased, checked, and published to the integration branch. The orchestrator itself is a static TypeScript daemon with named hook points for model-backed judgment, designed to converge to the same outcome after a crash at any point. Task graphs are imported from Linear, Jira, or GitHub Issues through the session's own tracker connector (the `gh` CLI for GitHub), and progress is mirrored back to the tracker.

## Running locally

Prerequisites: Node 22.13 or newer (the store uses Node's built-in SQLite), git, and, for real agents, the Claude Code CLI (`claude`) logged in, or for Codex workers (`runner.kind: codex`, or tasks with `runner: codex`) the Codex CLI (`codex`) on PATH and logged in. Scripted agents need nothing else. Start from a Claude Code session with the plugin, or from a terminal with the CLIs.

### From a Claude Code session

Install the plugin from this repository's marketplace. Nothing else needs to be installed or on PATH:

```
claude plugin marketplace add autodidacticon/orchestrator
claude plugin install orchestrator@orchestrator
```

From a checkout instead, run `npm install && npm run build` once, then `claude --plugin-dir /path/to/orchestrator/hosts/claude-code`.

Then use the skills: `import` turns a Linear or Jira epic, or a GitHub issue or milestone with its sub-issues, into the graph with the session's own tracker connector, `run` starts the daemon, has the session's own subagents execute the launches through a bundled workflow, and monitors (questions, reviews, stuck tasks, proposals, tracker mirroring), `work` adds workers from another session or switches the mode, and `review` judges a milestone's pinned commit. On `start` the daemon detects the repository's check command, integration branch, and the tools agents may run, and the skill reports them with their sources; when nothing supplies a check command, the skill looks in `CLAUDE.md`, the README, and the root manifests and sets it through `configure`, or asks. No `orchestrator.yaml` is needed; the terminal section below describes the resolution order and the overrides. The plugin's launcher (`hosts/claude-code/bin/orchestrator.mjs`) runs the package from the plugin's own `node_modules` after a marketplace install (Claude Code installs the published package `@autodidacticon/orchestrator` pinned in `hosts/claude-code/package.json`), from the checkout when loaded with `--plugin-dir`, and through `npx` as a fallback.

A Codex session can be the operator too: [hosts/codex/README.md](hosts/codex/README.md) registers the operator server as `[mcp_servers.orchestrator_operator]` in `~/.codex/config.toml`, with a `tool_timeout_sec` above the `wait` cap, or with `codex mcp add` and a lowered `ORCH_WAIT_CAP_MS`. It also links the `orchestrator-import`, `orchestrator-run`, and `orchestrator-review` skills into `~/.codex/skills`. Those skills start a fresh run in `spawn` mode (unless `orchestrator.yaml` sets `runner.mode`), because a Codex session has no subagents to work launches. They read the test command from `AGENTS.md`. Under `codex exec` the operator tools need pre-granted approvals.

Who executes launches is `runner.mode`: `pull` parks each prepared launch until a worker claims it, and is what a run started from the plugin defaults to, with the `run` skill's workflow claiming launches for visible session subagents; `spawn` has the daemon run headless Claude Code or Codex agents, and is the default for `orchestrator-ctl start` from a terminal, where no session is attached, and for a plugin-started run whose runner kind is `codex` (the `start` tool's `runnerKind` argument, or already in force for the run), because the plugin's pull-mode workers are the session's Claude subagents, which claim only `claude-code` launches; codex launches in `pull` are worked by the Codex work loop (`orchestrator-work`, [hosts/codex/README.md](hosts/codex/README.md) section 4), started from a shell, which claims with `runner: "codex"`, runs `codex exec` per claim with the spawned launch's command, and posts the usage back; `mixed` parks for `runner.claimWindowMs` (default 60 s) and then spawns. `runner.mode` in `orchestrator.yaml`, `orchestrator-ctl mode <mode>`, or `start` with `mode` are explicit choices that the plugin default never overrides. A claimed launch has no process: its lease is renewed by the worker's API calls and by progress in the worktree, and `release` hands it back (untouched: no attempt spent; with `--keep`, or `keep: true` on the tool, uncommitted work is committed on the launch branch, the branch is kept, and the task returns to unstarted at no cost with an `interrupted` context in its next brief, up to `daemon.maxKeptReleases` times, default 3).

### From a terminal

Build the package and put its executables on PATH:

```
git clone git@github.com:autodidacticon/orchestrator.git && cd orchestrator
npm install
npm run build
npm link            # puts orchestrator, orchestrator-ctl, orchestrator-mcp, orchestrator-mcp-shim on PATH
```

1. No configuration file is needed. At every start the daemon reads the repository root (never subdirectories) and detects the check command from the first matching manifest in a fixed order (a `Makefile` with a `test` target, then `package.json` with a real `test` script using the package manager named by `packageManager` or the lockfile, then `Cargo.toml`, `go.mod`, `pyproject.toml`/`setup.cfg`/`pytest.ini` with uv or poetry when their lockfile exists, `Gemfile`, `build.gradle(.kts)`, `pom.xml`, `mix.exs`, `*.sln`/`*.csproj`), the integration branch (`origin/HEAD` when that branch exists locally, else the checked-out branch, else `main`), and the tools spawned agents may run (`Bash(git:*)` and the orchestrator tools, plus the test, run, install, and exec commands of every toolchain found: `npm test`, `npm run`, `npm install`, `npm ci`, `npx`, `node`, `cargo`, `go`, `pytest`, `python`, `pip`, `uv`, `poetry`, `make`, and their counterparts). Every value is resolved in one order, an explicit argument over `orchestrator.yaml` over the branch pinned for the run (integration branch only) over detection over the built-in default, and records where it came from. Arguments are durable overrides for the run: `orchestrator-ctl start --set checkCommand="make check" --set capacity=3` (also `integrationBranch`, `allowedTools` as a JSON array or one rule per flag, `runnerCommand`, `runnerKind`, `model`, `effort`, and the per-kind keys `claude.model`, `claude.effort`, `claude.commit`, `codex.model`, `codex.effort`, `codex.sandbox`, `codex.commit`, `codex.command`), and `orchestrator-ctl config --check-command ... --capacity ... --allow "Bash(docker:*)" --runner-command ... --runner-kind codex --model ... --effort ... --sandbox ... --commit agent|daemon --clear <key>` on a running daemon (`--sandbox` sets `codex.sandbox`, `--commit` the commit policy of the kind in force, and `--clear` also takes a per-kind key such as `codex.sandbox`); `orchestrator-ctl config` alone prints every key with its value and source, the detection record, and `needsConfig`. The same facts are in `status` (`config`, `toolchain`, `needsConfig`) and in `config.json` in the run directory. When nothing supplies a check command, `needsConfig` names it and submitted work is held, without spending an attempt, until one is set. The integration branch is pinned when the run first starts: a re-pointed `origin/HEAD` or a different checked-out branch never moves it, and an explicit different branch is refused once the run holds launches (start from a fresh run directory to change it). The derived allow list lets spawned agents fetch and run packages, including their install scripts, with the user's credentials; `runner.claude.deriveTools: false` with an explicit `runner.claude.allowedTools`, or a `deny` rule in the project's `.claude/settings.json`, narrows it. Which agents get the list is the runner mode: it is filled into the `{allowedTools}` slot of the default `runnerCommand` for launches the daemon spawns (`spawn`, and `mixed` after the claim window), while a launch claimed by a session worker runs under that session's own permissions (see the previous section). Workers run `claude-opus-5-5` at `medium` effort by default (`runner.claude.model` and `runner.claude.effort`, overridable the same way); a task chooses its own with `model` and `effort` in its payload, which the import fills from `model:<name>` and `effort:<level>` labels on the issue. A task can also choose its runner kind with `runner: codex` (or `claude-code`) in its payload or a `runner:<kind>` label, so one run can mix Claude Code and Codex launches; a task without a `model` or `effort` then gets the chosen kind's defaults. The choice is fixed when a launch is prepared, filled into the `{model}` and `{effort}` slots of the default `runnerCommand` for spawned agents, carried in the claim response for session workers, and shown per launch in `status`. An existing `orchestrator.yaml` keeps working unchanged: keys it sets resolve with source `file`, and a `runnerCommand` without the `{allowedTools}`, `{model}`, or `{effort}` slots runs verbatim. The file is optional for everything else too:

   ```yaml
   integrationBranch: main
   checkCommand: npm test          # run on every rebased submission before it is published
   apiBind: 127.0.0.1              # the address the API binds; 0.0.0.0 in a cluster (file key, read at start)
   apiBaseUrl: http://orchestrator.orch.svc:8080   # the URL advertised to agents and clients when it differs from the bind
   capacity: 2                     # agents in parallel
   runner:
     kind: claude-code                    # or codex; a task's `runner` payload key or `runner:<kind>` label overrides it
     claude:
       allowedTools: ["Bash(docker:*)"]   # appended to the derived list for spawned agents
       deriveTools: true                  # false: only Bash(git:*), the orchestrator tools, and the rules above
       model: claude-opus-5-5             # worker model; a task's `model` payload key or `model:<name>` label overrides it
       effort: medium                     # low, medium, high, xhigh, or max; a task's `effort` key or `effort:<level>` label overrides it
     codex:
       model: gpt-6-astra                 # the Codex default model
       effort: medium                     # low, medium, high, xhigh, max, or ultra
       sandbox: workspace-write           # read-only, workspace-write, or danger-full-access
   scheduling:
     order: [criticalPath, priority, fifo]   # admission order; ties keep graph file order
     scopes: true                  # never run two tasks whose declared scopes overlap
   budgets:
     maxLaunchMs: 7200000          # 2 h per launch
     maxRunCostUsd: 20             # pause admission when the run has spent this much
     prices:                       # USD per million tokens, for runners that report tokens but no cost (Codex)
       gpt-6-astra: { inputPerMTok: 1.25, cachedInputPerMTok: 0.125, outputPerMTok: 10 }   # illustrative rates
   ```

   `runner.kind` picks the agent CLI: `claude-code` (the default) or `codex`, each with its own block, default model, and effort levels (Codex adds `ultra`). Select it in the file, or at runtime with `--set runnerKind=codex`, `orchestrator-ctl config --runner-kind codex`, the plugin's `start` or `configure` tool with `runnerKind: "codex"`, or `PUT /v1/config { runnerKind: "codex" }`; a flat `model` or `effort` argument binds to the kind in force, and `--set codex.model=...` (or `codex: { model, effort }` on the tools) names a kind's key directly. Under `codex` no allow list is composed (`config.allowedTools.applied` is false), and the daemon spawns `codex exec` for each launch. Codex reports token counts rather than a cost, so a Codex launch is priced from `budgets.prices` for its model; without a price its cost stays unknown and it is counted in `cost.unpricedLaunches`.

   ```yaml
   runner:
     kind: codex
     codex:
       model: gpt-6-astra        # the Codex default
       effort: medium            # low, medium, high, xhigh, max, or ultra
       sandbox: workspace-write  # read-only, workspace-write, or danger-full-access
       # commit: daemon          # unset: daemon, or agent under danger-full-access
   ```

   Each kind has a commit policy, `runner.<kind>.commit`: `agent` (the agent commits before it submits) or `daemon` (when the agent submits, the daemon commits what it left as `orchestrator` with the report summary as the message, and `agent.report` records `committedByOrchestrator: true`). `runner.claude.commit` defaults to `agent`. `runner.codex.sandbox` defaults to `workspace-write`, and `runner.codex.commit`, when unset, is derived from the sandbox: `daemon`, or `agent` under `danger-full-access`. The reason is a known limitation of Codex's `workspace-write` sandbox: it cannot `git commit` in a linked worktree. The index lock under `<repo>/.git/worktrees/<wt>/` is refused, and `--add-dir` or `writable_roots` do not help, because Codex keeps the gitdir read-only. A clean worktree is never committed, so a no-op still needs `noChanges`. All three keys can be changed at runtime (`--set codex.sandbox=...`, `--set codex.commit=...`, `--set claude.commit=daemon`) and apply to launches prepared afterwards. `danger-full-access` gives Codex the same unsandboxed access the Claude runner has; whether `git commit` works under it has not been probed.

2. Start the daemon for that repository. It records run data under `~/.orchestrator/runs/<id>/` and prints the graph file path:

   ```
   cd /path/to/your/repo
   orchestrator-ctl start          # {"started": true, "url": "http://127.0.0.1:...", "graphPath": "~/.orchestrator/runs/<id>/graph.yaml", ...}
   ```

3. Write the task graph to that `graphPath`. The daemon re-reads it on change. Every task needs a description and acceptance criteria, or it is blocked as under-specified:

   ```yaml
   nodes:
     - id: T1
       title: Add the schema migration
       description: Create the users table migration and the model.
       acceptanceCriteria: [migration applies cleanly, model has unit tests]
       deps: []
     - id: T2
       title: Expose the users API
       description: Add GET and POST /users on top of T1's model.
       acceptanceCriteria: [endpoints documented, integration test passes]
       deps: [T1]
       scope: ["src/api/**", "package.json"]   # optional: path globs the work stays within
       priority: 1                             # optional: lower is more urgent
     - id: MVP
       kind: milestone
       gated: true                 # a human reviews and accepts the pinned commit
       deps: [T2]
   ```

4. Operate the run from the same terminal:

   ```
   orchestrator-ctl status                         # sets by state, stall roots, open questions, stuck tasks, deferred tasks, cost, config, toolchain, needsConfig
   orchestrator-ctl config [--check-command <cmd>] [--allow <rule>] [--capacity <n>] [--runner-kind <kind>] [--sandbox <mode>] [--commit <policy>] [--clear <key>]   # show or override the configuration
   orchestrator-ctl answer T1 "use sqlite"         # answer an agent's question
   orchestrator-ctl logs T1                        # the agent's captured output
   orchestrator-ctl nudge T1 "commit what you have"
   orchestrator-ctl accept MVP --sha <sha> --version 1   # or: reject MVP --note "..."
   orchestrator-ctl reopen T1 [--cascade]
   orchestrator-ctl proposals | accept-proposal <id> | reject-proposal <id> --note "..."
   orchestrator-ctl pause | resume [--override-budget]
   orchestrator-ctl mode pull | claim w1 | release <launchId> --reason "..."
   orchestrator-ctl stop [--reap]                  # graceful: agents keep running and are adopted on the next start
   orchestrator-ctl runs                           # every run under ~/.orchestrator
   ```

   The daemon exits on its own after `daemon.idleExitMs` (default 10 min, 0 disables) with nothing live and no session attached (`daemon.exitWhileAttached: true` lets it exit while one is), records why in `daemon.json` (`runs` shows `exit` for a daemon that is gone, or nothing after a crash), and any `orchestrator-ctl` command or plugin tool revives it on demand; only an explicit `stop` is final until the next `start`. `status` reports `idle` and `attachments`. To run the daemon in the foreground instead, `orchestrator --repo .` (SIGTERM stops it gracefully). To keep everything inside one directory, use a config with explicit paths and `orchestrator --config orchestrator.yaml` with `repoPath`, `graphPath`, and `dataDir` set; then pass `--data-dir` to `orchestrator-ctl`.

By default agents are headless Claude Code sessions (`runnerCommand`, with `{allowedTools}`, `{model}`, and `{effort}` filled at spawn), or headless Codex sessions (`codex exec`) under `runner.kind: codex`, each in its own git worktree with the brief on stdin and the agent API as an MCP server. For a dry run without model calls, point `runnerCommand` at the scripted agent: `node --import <repo>/node_modules/tsx/dist/loader.mjs <repo>/test/agents/scripted.ts {briefJson}`, and give each task a `behavior` such as `commitAndSubmit`, `blockAndWait:<question>`, or `fail`.

### Tests

`npm test` runs everything that needs no model: unit tests, slices with real subprocess agents, git, and the HTTP API, and the crash-injection suite in `test/crash`, which is the project gate. Seven opt-in tests use a real model: `ORCH_E2E_CLAUDE=1 npm test -- test/e2e/claude` runs three Claude Code agents, `ORCH_E2E_CLAUDE_PLUGIN=1 npm test -- test/e2e/plugin` has a Claude Code session operate a run through the plugin, and `ORCH_E2E_CLAUDE_WORK=1 npm test -- test/e2e/work` has a session execute a run in pull mode with two workers through the work skill. `ORCH_E2E_CODEX_OPERATOR=1 npm test -- test/e2e/codex-operator` has `codex exec` operate a spawn-mode run of scripted agents through the operator server to `finished`. `ORCH_E2E_CODEX=1 npm test -- test/e2e/codex` has Codex workers (a logged-in `codex` on PATH; skipped with a warning without one) publish three tasks plus a fourth whose `block` is answered after 90 s, and checks recorded tokens, the daemon commit policy, and the MCP tool timeout. `ORCH_E2E_CODEX_WORK=1 npm test -- test/e2e/codex-work` has two Codex work loops drain a three-task pull-mode graph. `ORCH_E2E_OPENCODE=1 npm test -- test/e2e/opencode` has OpenCode workers on the free model `opencode/big-pickle` (no login or key needed; skipped with a warning naming `opencode` when it is not on PATH) publish three tasks at capacity 2, one of whose `block` is answered after 75 s, and checks recorded tokens with cost 0 from the stream, the agent commit policy, and that `startupContended` relaunches are not charged. A second case, a `needsAccess` question for a command outside the derived permission patterns, is skipped: opencode 1.18.30 ends a run on an auto-rejected `ask`. `ORCH_E2E_OPENCODE_RECORD=1` also copies the launches' JSONL, redacted, to `test/fixtures/opencode/e2e-*.jsonl`. One more opt-in check uses no model: `ORCH_E2E_CODEX_HOST=1 npm test -- test/host/codex-host` runs `codex mcp get` against the host's config template and lets the installed `codex` render the template's SessionEnd hook (skipped with a warning without a `codex` on PATH).

### Running on Kubernetes

The daemon also runs as a long-lived container. `deploy/README.md` is the operational reference: the `Dockerfile` builds an image with Node, git, and ssh only (`orchestrator` and `orchestrator-ctl` on PATH); `deploy/base` is a kustomize layout with a Recreate Deployment that clones `REPO_URL` into a volume, probes `/healthz` and `/readyz`, and runs in pull mode behind a ClusterIP Service; `deploy/overlays/kind` adds an in-cluster git origin and a one-task graph; and `deploy/smoke.sh` builds, loads into kind, applies the overlay, and asserts the milestone claims over the API (`--dry-run` prints the steps). The cluster-facing settings are `apiBind` and `apiBaseUrl` (the address the API binds and the URL it advertises; file keys read at start, not runtime overrides), `ORCH_LOG_FORMAT=json` for one JSON object per log line, and `ORCH_URL` on a client naming a non-loopback host, which makes `orchestrator-ctl` and the operator MCP server use that daemon without ever starting a local one. Workers do not yet run in the cluster: a daemon there parks launches for session workers, and the mounted graph is read-only, so import and proposal acceptance fail in that layout until the graph lives in the store. The specification is [cluster-runtime](openspec/specs/cluster-runtime/spec.md) and the "Container mode" requirement of [operator-control](openspec/specs/operator-control/spec.md).

## Behaviour

A task is done once its sealed work has been rebased onto the integration branch, checked, and published as one squash commit with `Orchestrator-Task` and `Orchestrator-Launch` trailers; a gated milestone then waits for a human to accept its pinned commit. The daemon converges to the same outcome after a crash at any named point, and surviving agents are adopted on restart.

Child processes. Spawned agents and check commands inherit the daemon's environment with `ORCH_HOME` pointed inside the run's data directory and the client-side variables (`ORCH_URL`, `ORCH_REPO`, `ORCH_DATA_DIR`) removed, so repository code they run cannot discover or stop the user's daemons; `ORCH_API` stays, since the agent shim needs its own daemon. A `shutdown` through the route records who asked (attachment id, remote address, user agent) in an `operator.shutdown` event and in the exit record, and the revival refusal after a stop names the caller.

Tracker sync. After an import that names its tracker, the daemon derives tracker-bound effects from its own transitions into a durable outbox, in the same transaction as the transition: an issue goes in progress on its first launch, done when its work is published (or, with `tracker.doneAt: milestoneAccepted`, when its gated milestone is accepted), cancelled on cancel; the parent issue follows its first starting child and closes when the milestone is accepted. Comments are posted where a human is needed: an agent's question, a block with its reason, a milestone ready for review, accepted, or rejected (`tracker.commentOnDone` and `tracker.commentOnFail` add completion and failure comments, both off by default). The daemon never talks to a tracker: the `run` skill drains the outbox after every `wait` with the session's Linear or Atlassian tools, mapping states by type, and acknowledges each effect (`outbox`, `ack` tools; `GET /v1/outbox`, `POST /v1/outbox/:id/{ack,nack}` routes; `orchestrator-ctl outbox | ack`). Every comment ends with a marker line, `— orchestrator run <id> · event <n>`, so a drainer can recognise its own comments and never posts one twice. A human reply under a question comment is relayed as the answer (`tracker.answersFromComments`, default on); the first answer wins. Config keys: `tracker.enabled` (`auto` | `always` | `never`), `maxAttempts`, `parentInProgress`, `doneAt`, `commentOnDone`, `commentOnFail`, `answersFromComments`. Status reports `tracker`, `outboxPending`, and `trackerErrors`. Manual check against a sandbox workspace: import an epic with the `import` skill in a Claude Code session connected to Linear or Jira, run it with the `run` skill, and watch the child issues move and the question comment appear; this is not part of `npm test`.

The daemon's life. A session attaches through the plugin's operator server, which registers its process ancestry with the daemon on first contact and ends the attachment when its transport closes; the plugin's `SessionEnd` hook posts the ending session's ancestry as well, and the daemon ends any attachment whose own process has died. A claim made through a session carries its attachment, and when the attachment ends the daemon releases that launch with `keep` on the next tick: uncommitted work becomes a work-in-progress commit on the launch branch, the worktree goes, the branch stays, the task returns to `unstarted` with `attempts` unchanged and an `interrupted` context (prior launch, branch, head, the WIP commit) in its next brief, counted in `interruptions` and bounded by `daemon.maxKeptReleases`. With nothing live, no verifier job pending, no cascade pending, no request in flight, and no session attached, the daemon exits after `daemon.idleExitMs`, writes an exit record, and is revived by the next operator call; the plugin's `SessionStart` hook names runs whose daemon is alive or whose last exit left parked launches, open questions, a milestone under review, or a stall. Releasing a new version: bump the version in `package.json`, `hosts/claude-code/.claude-plugin/plugin.json`, and the pins in `hosts/claude-code/package.json` and `hosts/codex/package.json`; `npm publish` (which builds); regenerate `hosts/claude-code/package-lock.json` with `npm install --package-lock-only` in that directory against the published version; then push.

Scheduling. Ready tasks are admitted in the order of `scheduling.order`, a chain of stages applied as one stable sort (default `[criticalPath, priority, fifo]`): `criticalPath` puts the task with the longest chain of tasks behind it first, so the chain that gates the milestone starts first; `priority` reads the task's `priority` as a number, lower first, missing last (the import passes the tracker's number through, dropping Linear's 0); `fifo` is graph file order, which also breaks any remaining tie. Waiting tasks whose answer has arrived are resumed before anything is ordered; `order: [fifo]` restores the v1 order. A task may declare `scope`, a list of path globs (in the graph file, or under a `Scope` heading in an imported description, one glob per bullet; `options.scopeHeading` renames it). While a task is running, waiting, submitted, or has a claimable launch, no task whose scope overlaps it is launched: two globs overlap when the static prefix of one (the leading path segments before any `*`, `?`, `[`, `{`) is a prefix of the other's, so `src/**` holds `src/api/x.ts`, `src/api/**` and `src/ui/**` run together, and `**` or `*` overlaps everything. Held-back tasks appear as `deferred: [{ id, reason: scopeOverlap, with }]` in status and as a count in the digest; they launch on the first tick after the blocker publishes. `scheduling.scopes: false` turns the filter off; a malformed `scope` fails graph validation.

Health. The daemon renews a launch's lease every tick while its process is alive, so a quiet agent is never failed for silence; lease expiry applies only to launches the runner cannot observe. Progress is a worktree fingerprint (head plus status and diff), any API call, or a changed heartbeat text. A launch idle past `health.stuckAfterMs` (default 15 min) is flagged (`stuck` in status and the digest, a `stuck` notice in its inbox, event `launch.stuck`) and idle past `health.stuckFailAfterMs` (default 45 min) is reaped and failed with reason `stuck`, spending an attempt; either threshold at 0 disables that step. `orchestrator-ctl nudge <task> <message>` (also the `nudge` tool) queues a message for the agent's inbox. Budgets: `budgets.maxLaunchMs` (default 2 h) fails an overlong launch with reason `timeBudget`, waiting time excluded; `budgets.maxRunCostUsd` (default 0, unlimited) pauses admission with `pausedReason: costBudget` once the run's cost, read per launch from Claude Code's final JSON or computed from Codex's token counts times the `budgets.prices` entry for the launch's model, reaches the ceiling (an unpriced Codex launch has no cost and is counted in `cost.unpricedLaunches`), and `resume` is refused until `orchestrator-ctl resume --override-budget` (or `resume` with `overrideBudget`) raises the ceiling by one budget. When a task is published, every other running agent gets a `baseMoved` notice naming the new head and the files it touched, and may rebase its branch onto it; the verifier rebases from the merge base so such branches integrate cleanly (`health.baseMovedNotice` turns the notice off).

Graph mutation. Milestones hold no work, so they never block a reopen: reopening a done task resets every done or submitted milestone downstream (`milestone.reset`), which is reviewed again at its next version once the revised work is published, and dependency edits to such milestones are compatible reloads that reset them the same way. A reopen whose target has started task dependents is refused with the blockers; `orchestrator-ctl reopen <task> --cascade` (or `reopen` with `cascade: true`) records a plan, returns it as `reset: [{ id, from }]`, and the next tick kills running dependents, drops queued verification, and returns done dependents and the target to unstarted with budgets reset. Nothing on the integration branch is reverted: each relaunch is briefed with a revision context naming the prior launch, branch, published commit, and report, and publishes a further trailer commit. Agents may put structured `proposals` (title, description, acceptance criteria, optional deps, scope, labels) in their submit report; they are held pending (`proposals` in status and the digest) until `accept-proposal <id> [--node-id <tracker key>]` appends a task node depending on the proposer, joining its gated milestone when `proposals.joinMilestone` is true (default), or `reject-proposal <id> --note`. A compatible reload that edits a running task's payload sends its agent a `payloadChanged` inbox notice (`graph.payloadChangedNotice`, default true); the pinned brief stays and the next launch uses the new payload.
